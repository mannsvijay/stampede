# Design decisions

Write these yourself, in your own words. Each one is an interview answer you've already rehearsed.

## Template
### D-000 Title
- **Date:**
- **Context:** what problem forced a choice
- **Options considered:** at least two
- **Decision:**
- **Why:** the trade-off in one or two sentences
- **How I'd know it was wrong:** a measurement or symptom

---

### D-001 Modular monolith instead of microservices
- **Date:** 2026-11-07
- **Context:** I'm one person with about twelve weeks. The hard part of this project is contention:
  many buyers racing for the same seats. Splitting the system into services is a different problem.
- **Options considered:** microservices; a plain monolith with no internal boundaries; a modular
  monolith with enforced boundaries.
- **Decision:** One Spring Boot app split into eight modules (identity, inventory, booking, payments,
  ticketing, waitingroom, realtime, control). Modules talk only through each other's public API package
  or through events, and a Spring Modulith test fails the build if a module reaches into another.
  I run it as three identical instances behind Nginx.
- **Why:** Microservices would cost me network calls, distributed transactions and deployment work
  without teaching me anything more about contention. A plain monolith turns into a tangle. With
  enforced modules, I get clean boundaries now and could still split a module out later.
- **How I'd know it was wrong:** One module needs to scale differently from the rest. For example,
  waitingroom or realtime saturates the CPU while booking sits idle, so I'm forced to scale everything
  to scale one thing. Or the Modulith test keeps pushing me into workarounds that make the code worse.

### D-002 UUID v4 ids, generated by the app
- **Date:** 2026-11-08
- **Context:** Every table needs a primary key type, and I wanted one type everywhere.
- **Options considered:** bigint identity; UUID v4; UUID v7 (time-ordered); a hybrid with bigint for
  internal tables and UUIDs for public ones.
- **Decision:** UUID v4 everywhere. The app creates ids with `UUID.randomUUID()`, and
  `gen_random_uuid()` is the column default for rows inserted straight from SQL.
- **Why:** In the Redis-first strategy, the Lua script creates a hold before Postgres knows about it,
  so the id must exist before the insert. UUIDs also can't be guessed in URLs, so `/orders/1042`
  doesn't leak my sales volume. The cost is 16 bytes per id, and random values spread inserts across
  the index instead of appending at the end.
- **How I'd know it was wrong:** The benchmarks show index bloat or slow inserts on the busy tables
  (holds, order_items, outbox). Then I'd switch to UUID v7, which needs no migration because the
  column type stays `uuid`.

### D-003 Seat states narrowed to AVAILABLE / HELD / SOLD
- **Date:** 2026-11-08
- **Context:** The PRD's seat diagram also has CHECKED_IN and TRANSFERRED. But a checked-in or
  transferred seat is still sold. Those two states describe the ticket, not the seat.
- **Options considered:** keep all five states on `event_seats`, as the PRD draws it; keep only
  AVAILABLE/HELD/SOLD on the seat and move the rest to tickets.
- **Decision:** `event_seats.status` is AVAILABLE, HELD or SOLD. Tickets have ISSUED, CHECKED_IN or
  REVOKED. A transfer keeps the same ticket row and bumps its version and holder.
- **Why:** With five seat states, every "is this seat sold?" query and every invariant (for example,
  "every sold seat has a paid order") has to remember that three values mean sold. Keeping the seat to
  the three states that matter for contention keeps the hot path and the checks simple.
- **How I'd know it was wrong:** Seat-map or gate views keep joining tickets just to show a seat's
  state, or I find a rule that genuinely depends on the seat, not the ticket, being checked in.

### D-004 Seat transition guard in code, not a database trigger
- **Date:** 2026-11-08
- **Context:** The PRD says transitions are guarded "in code and in the database". A CHECK constraint
  can only limit which values are allowed. Stopping an invalid move such as SOLD to HELD in the
  database would need a `BEFORE UPDATE` trigger on `event_seats`.
- **Options considered:** a trigger that rejects transitions not in the diagram; a state machine
  class in code (M1.1) only, plus database constraints on the data itself.
- **Decision:** The guard lives in code. The database still enforces what it can check on a single
  row: the CHECK that ties status to `hold_id`/`order_id` (HELD needs a hold, SOLD needs an order), and
  the unique partial index on active order items.
- **Why:** `event_seats` is the hottest write path in the system. A trigger would run on every hold
  under contention and skew the benchmark that compares strategies. The trade-off is that code
  bypassing the state machine could make a bad transition without the database objecting. The index
  and the invariant checker after every test are my safety net.
- **How I'd know it was wrong:** The invariant checker catches a bad transition that came from code
  skipping the guard. Or I measure the trigger and its cost is negligible, in which case I'd add it.

### D-005 Per-user ticket cap via a counter row
- **Date:** 2026-11-08
- **Context:** The per-user cap has to hold under concurrency. If a user's cap is 4, two parallel
  requests can each count "2 already held", both see room, and both add 2 more, for 6 in total. No
  single-row constraint can see across those requests.
- **Options considered:**
  - Count holds and orders, then insert: races under READ COMMITTED, exactly as above.
  - `SELECT … FOR UPDATE` on the user row: serialises everything that user does, and that row
    belongs to the identity module.
  - SERIALIZABLE isolation: correct, but it forces retries and is harder to reason about.
  - A counter row per (event, user).
- **Decision:** I use a `user_event_allowance(event_id, user_id, used)` table with `CHECK (used >= 0)`.
  In the same transaction as the hold, I run
  `UPDATE … SET used = used + n WHERE used + n <= limit`. Zero rows updated means `LIMIT_EXCEEDED`.
  Releases and expiries decrement the counter. The Lua strategy keeps the same counter as a Redis key,
  checked inside the script.
- **Why:** A conditional UPDATE does the check and the increment in one atomic step. Postgres locks
  the row, makes the second request wait, and re-checks the WHERE against the new value. Requests only
  contend for the same user and event, so this doesn't slow the drop down for anyone else.
- **How I'd know it was wrong:** The concurrency test shows a user ending up over the cap. Or the
  invariant check finds `used` drifting from the user's real active holds and orders, probably
  because some release path forgot to decrement.
- **Implemented in M1.4 (D-016):** one upsert inside the strategy's transaction (it also creates the
  row on a user's first hold); every release reason decrements; harness invariant I8 checks the
  counter against active holds after every round.

### D-006 Name-based UUIDs for seed data (an exception to D-002)
- **Date:** 2026-11-08
- **Context:** The seed loader has to be idempotent: running it twice must not create a second venue.
  Sections, seats and tiers have natural unique keys, but venues and events don't, so a second run
  couldn't tell it had already created them. The k6 load tests (M2.4) also need to know seat ids in
  advance.
- **Options considered:** name-based UUIDs for seed rows; a V2 migration adding unique `slug`
  columns to venues and events (ids stay random v4); looking rows up by name before inserting, with no
  constraint behind it.
- **Decision:** Every seed row gets a version 3 UUID made from its name, for example
  `UUID.nameUUIDFromBytes("stampede-seed:seat:demo-arena:FL-L:A:1")`. Inserts use
  `ON CONFLICT (id) DO NOTHING`, then the loader reads everything back and fails, rolling back, if the
  database doesn't match the file. Rows the app creates at runtime still use random v4 ids (D-002).
- **Why:** The same file gives the same ids on every machine, so loading is naturally idempotent with
  no schema change, and load tests can target known seats. Looking up by name has no constraint behind
  it, so it can still duplicate rows. The costs: seed ids can be guessed (fine, since seed data is
  public demo data), v3 uses MD5 (fine for naming rows, never for security), and renaming a slug or
  section code changes every id under it.
- **How I'd know it was wrong:** I need to edit loaded venues in place (for example, the venue editor in
  O5) and keep finding myself fighting fixed ids. Or real, non-seed data starts depending on the
  `stampede-seed:` naming scheme.

### D-007 Module APIs as named interfaces, with an enforced dependency table
- **Date:** 2026-11-08
- **Context:** D-001 says modules talk only through public APIs or events. Spring Modulith can check
  that, but I have to choose what counts as a module's public API, and which module may depend on
  which. Some modules should only *react* to another module's events, never call it.
- **Options considered:** (A) Modulith's default: a module's top-level package is its API and
  subpackages are internal; (B) explicit `api` and `events` subpackages marked `@NamedInterface`,
  with nothing public in the top-level package; (C) the top-level package as the API plus one
  `events` named interface.
- **Decision:** Option B. `<module>.api` holds what other modules may call, `<module>.events` holds
  the events it publishes. Everything else (including `inventory.seed`) is internal. Each module's
  `package-info.java` declares `@ApplicationModule(allowedDependencies = ...)` and `ModularityTest`
  runs `ApplicationModules.verify()`. The full table is enforced from day one:

  | Module | May call (`::api`) | May listen to (`::events`) |
  |---|---|---|
  | identity | none | none |
  | waitingroom | identity | none |
  | inventory | waitingroom | none |
  | payments | none | none |
  | ticketing | identity | none |
  | booking | inventory, payments, ticketing | inventory, payments |
  | realtime | none | inventory, waitingroom, booking |
  | control | waitingroom, inventory, booking, payments, ticketing | waitingroom, inventory, booking, payments, ticketing |

  The table is a DAG. Booking orchestrates the saga by calling inventory, payments and ticketing and
  reacting to their events; none of them depend on booking. Payments gets the order id and amount as
  arguments, and control drives chaos settings through payments' API, so payments depends on nothing.
  An explicit `allowedDependencies = {}` means "nothing allowed"; leaving the attribute out would mean
  "anything allowed", so every module declares it.
- **Why:** With a single public package, a dependency is all-or-nothing, so "realtime may only listen
  to inventory" would be a comment. Named interfaces let the test tell calling apart from listening.
  The cost is a bit of ceremony (a `package-info` per interface) and remembering that event classes
  live in the publisher's `events` package, so a listener depends on the publisher.
- **Limit: table ownership is a convention.** Modulith analyses Java type references, not SQL. If
  booking runs `SELECT ... FROM event_seats` through JdbcClient, the test can't see it. Each module's
  `package-info` lists the tables it owns, and other modules must go through its API instead.
- **How I'd know it was wrong:** I keep adding allowances just to get features through, or I invent
  awkward events purely to avoid a "may call" edge. Or a code review finds a module querying another
  module's tables, which means the convention needs a check of its own (for example, separate DB
  schemas per module).

### D-008 Auth: short-lived JWTs, rotating refresh tokens, one lock row per session
- **Date:** 2026-11-08
- **Context:** PRD 11 asks for short-lived JWTs with rotating refresh tokens and bcrypt or Argon2.
  Three API instances must verify tokens without sharing sessions, and a stolen refresh token must
  not give an attacker a session that outlives the user's.
- **Options considered:** Spring's OAuth2 resource server vs jjwt plus a hand-written filter; HS256
  vs an asymmetric key pair; bcrypt vs Argon2id; refresh token in an httpOnly cookie vs the response
  body; strict reuse detection vs a grace window for parallel refreshes.
- **Decision:**
  - Access tokens: HS256 JWTs (sub = user id, role, iss, iat, exp, jti), 15 minutes, signed with
    `STAMPEDE_JWT_SECRET` (at least 32 bytes; the app won't start without it). Verified by Spring's
    `BearerTokenAuthenticationFilter`, with the algorithm pinned, issuer and exp required, and 30 s
    of clock skew allowed.
  - Passwords: bcrypt cost 12, at least 12 characters, at most 72 UTF-8 bytes (bcrypt silently
    ignores the rest). Login gives the same answer for an unknown email and a wrong password, and
    compares against a dummy hash so timing doesn't tell them apart.
  - Refresh tokens: 32 random bytes, stored only as SHA-256, sent only in an httpOnly, Secure,
    SameSite=Strict cookie on `/auth`, with a required `X-Requested-With` header as a CSRF guard.
    7 days, renewed on every refresh, never past a 30-day cap per login.
  - Every refresh consumes its token and issues a child. Presenting a used token again (reuse)
    revokes the whole login session: we can't tell the real user from the thief, so both must log
    in again. This is strict: two tabs refreshing at the same moment also log the user out, so the
    frontend funnels refreshes through one shared call (M0.7).
  - A `refresh_token_families` table holds one row per login session (its 30-day cap and its
    revocation), and that row is the session's lock: every refresh and every revocation starts with
    `SELECT ... FROM refresh_token_families WHERE id = ? FOR UPDATE`.
  - 401, 403 and auth errors are problem+json with stable codes (PRD 10).
- **Why the family table exists:** the first version had only `refresh_tokens`, with the revocation
  on each token row, and the concurrency tests found two bugs in it:
  1. *Deadlock.* When 20 requests refresh the same token, one wins and 19 detect reuse and revoke
     the family with `UPDATE refresh_tokens SET revoked_at = now() WHERE family_id = ?`. That
     statement locks the family's rows in whatever order it scans them, so two revokers could each
     lock one row and wait for the other's. Postgres broke the cycle by killing one: a 500, in about
     one run in five.
  2. *Logout could miss a token.* A refresh consumes token P (locking P) while a logout runs that same
     UPDATE. The logout's statement only sees P, waits for P's lock, and meanwhile the refresh inserts
     child C and commits. The logout then revokes P and returns 204, but C was never in its snapshot
     and stays live. An attacker refreshing at the moment the user logs out would keep a session.

  With one lock row per family, everything that touches a family queues on that one row and runs one
  at a time. Each holder re-reads the token after getting the lock, so it sees what the previous
  holder committed. Revoking becomes a single-row update: a racing refresh either commits first (and
  its child belongs to a family that is then revoked, so it dies with it) or waits and sees the
  revocation. No transaction locks rows of two families, so there is no lock order to get wrong. The
  same idea as sorting seat ids before `FOR UPDATE` in the pessimistic strategy: make every
  competitor queue for the same thing first.

  Two details matter. It relies on READ COMMITTED (Postgres's default): the lock decides who goes
  next, but seeing the previous holder's writes depends on each statement after the lock taking a
  fresh snapshot. And under the lock, rotation also checks the family's own 30-day cap (a token
  never outlives its session) and consumes with `WHERE used_at IS NULL`, checking that exactly one
  row changed, so a future code path that forgets the lock fails loudly instead of consuming a
  token twice. A token that is both used and expired still counts as reuse and revokes the session.
  A correctness review found no bug in this design, but showed the original logout race test could
  not catch a broken logout (reuse detection revoked the family anyway); it now races exactly one
  refresh against one logout, and fails all 30 runs if logout is disabled.
- **Trade-offs:** an access token stays valid for up to 15 minutes after logout or role change (it is
  checked by signature only). Anyone with the HS256 secret can mint tokens, which is fine while only
  our own instances hold it. The refresh cookie needs the API and frontend to be same-site (M0.7
  proxy, M7.1 deployment). bcrypt cost 12 makes login slow on purpose (M2.4 logs in during k6 setup).
  `refresh_tokens` grows forever until a cleanup job deletes expired families (not built yet).
  Requests for one session queue on its lock while holding a DB connection; rate limiting (M4.3)
  is the defence against a flood for one session.
- **How I'd know it was wrong:** users report being logged out with several tabs open (reuse
  detection firing on benign races more than expected); the family lock shows up as a hotspot (it
  shouldn't, since only one user's session queues on it); or I need to revoke access tokens
  immediately (that would mean a denylist or much shorter access tokens).

### D-009 A small shared module for types every module needs
- **Date:** 2026-11-08
- **Context:** Almost every module will need to know who is calling, and every module returns errors
  with the stable codes from PRD 10. D-007 lets only waitingroom and ticketing depend on identity.
- **Options considered:** a `CurrentUser` type in `identity::api` (every module would need an
  identity allowance, rewriting much of D-007's table); a `shared` module; controllers reading the
  raw JWT themselves (no shared type, but claim parsing copied everywhere and tied to JWTs).
- **Decision:** A `shared` module with two named interfaces: `shared.security` (`CurrentUser`,
  `Role`) and `shared.error` (`ErrorCode`, `Problems`, `ApiException`). Identity's token converter
  puts a `CurrentUser` into the security context, so controllers in any module take
  `@AuthenticationPrincipal CurrentUser` without depending on identity. `shared` itself has
  `allowedDependencies = {}`, and every module lists `"shared :: security", "shared :: error"`
  explicitly. Rule: only types that every module needs go in shared, plus the internal web plumbing
  that applies those types to every module (amended by D-010): the application-wide problem+json
  handler, the `/error` controller and the OpenAPI error documentation, in the internal package
  `shared.web`. That package is not a named interface, so no module can reference it; Spring finds it
  by component scanning.
- **Why:** It keeps the D-007 graph unchanged and gives M0.6 a home for error handling. Probes showed
  how Modulith 1.4 treats it: types in shared's subpackages are internal unless marked as named
  interfaces; allowing just `"shared"` only covers its top-level package; `"shared :: *"` or naming
  each interface works. I chose explicit names because they are easy to search for and match how
  D-007 is written. `@ApplicationModule(type = OPEN)` also worked, but exposes every type in shared,
  which would let it quietly become a junk drawer.
- **How I'd know it was wrong:** shared starts collecting module-specific types (anything only one or
  two modules use belongs in that module's api), or a change to shared keeps forcing changes in many
  modules at once.

### D-010 Event read API, one problem+json handler, and a committed OpenAPI spec (DRAFT)
- **Date:** 2026-11-09
- **Context:** M0.6 adds the first public read endpoints (`GET /events`, `GET /events/{id}`) and
  replaces identity's scoped error handler with one for the whole app. M0.7 generates the TypeScript
  client from the OpenAPI spec, and PRD 10 says the spec is the source of truth, so the contract has
  to be fixed somewhere reviewable before the frontend starts.
- **Options considered:**
  - Spec: generate it from code with springdoc; write it by hand first and check the code against it
    (needs a contract-test library); generate it but commit the output and fail a test on drift.
  - Handler location: an internal `shared.web` package; a new `platform` module; the root
    `com.stampede` package (which Modulith doesn't verify at all).
  - Error codes: one central `ErrorCode` enum in shared; per-module code enums behind an interface.
  - Pagination: keyset cursor now; a hard cap now and a cursor later.
  - Availability counts (available/held/sold) in the responses: now; leave them to realtime.
- **Decision:**
  - **OpenAPI:** springdoc-openapi 2.10.0 (`-api` artifact, no Swagger UI; built against Spring Boot
    3.5.16, while the 3.x line targets Boot 4). The generated spec is committed at `docs/openapi.json`,
    and `OpenApiSpecTest` fails if the code generates anything else. M0.7 builds the client from the
    committed file, so every contract change shows up in a diff. `/v3/api-docs` is off unless the
    `openapi` profile is active. Errors are documented from the code: `@ErrorResponses({...})` on a
    controller method lists its codes, and each becomes a problem+json response under that code's own
    status, plus `500 INTERNAL_ERROR` on every operation. Response-only schemas mark every property
    required, because Jackson always writes every field (otherwise every generated TypeScript field
    would be optional). The server URL is a fixed `/` so the file doesn't change with the test's
    random port.
  - **Error handler:** `ApiExceptionHandler` in internal `shared.web`, extending Spring's
    `ResponseEntityExceptionHandler`, so every standard MVC error (404 route, 405, 415, malformed
    parameter) passes through one method that adds our `code` and a fixed message. Anything unexpected
    is a 500 with a generic message and an `errorId`; the exception goes only to the log. Security
    exceptions thrown inside a controller are rethrown so Spring Security still answers 401/403. A
    `ProblemErrorController` replaces Boot's `/error` page, which handles errors outside MVC (filters,
    `sendError`) and uses only the status. D-009's wording was amended to allow this.
  - **Error codes:** one central enum. New: `EVENT_NOT_FOUND`, `NOT_FOUND`, `METHOD_NOT_ALLOWED`,
    `UNSUPPORTED_MEDIA_TYPE`, `REQUEST_FAILED`, `INTERNAL_ERROR`.
  - **Read endpoints:** owned by inventory (D-007), in internal `inventory.catalog` with JdbcClient.
    The list is `{items, serverTime}`, capped at 100, ordered by drop time; it hides DRAFT, ENDED and
    already-started events. A DRAFT id gives 404, like an unknown id. The detail is read in one SQL
    statement. No availability counts.
  - **Demo times:** a dev-only `demo-reschedule` profile moves the demo event's drop and start back to
    now + the seed file's offsets, only while it is SCHEDULED.
- **Why:**
  - Generating the spec means it can't fall out of date. Committing it and testing for drift means
    nobody changes it without seeing the change, which keeps "the spec is the source of truth" honest
    without hand-writing YAML.
  - `shared.web` keeps the handler next to the types it applies, without a module that exists for two
    classes, and it stays under Modulith's checks (unlike the root package).
  - One code enum mirrors PRD 10's single table and gives the client generator one list.
  - `items` in a wrapper object lets a cursor arrive later without breaking clients.
  - Counts are stale as soon as they are sent, and counting `event_seats` on every board refresh adds
    reads to the hottest table during a drop.
  - One SQL statement for the detail: under READ COMMITTED, each statement sees its own snapshot, so
    two separate queries could see the event and its tiers at different moments.
- **Trade-offs:**
  - The drift test needs its own application context with the `openapi` profile, so it starts its own
    containers.
  - An intended API change takes two steps: change the code, then copy `build/openapi/openapi.json`
    over `docs/openapi.json`.
  - Response fields are typed as always present, which stays true only while response records don't
    use `@JsonInclude(NON_NULL)`.
  - Shared now depends on springdoc and Spring Security classes (libraries, not modules).
  - Security runs before routing, so anonymous callers get 401 instead of 404/405 (documented in PRD 10).
- **How I'd know it was wrong:**
  - The drift test gets "fixed" by copying the file without anyone reading the diff, so the committed
    spec stops being a real review point.
  - `shared.web` starts collecting non-error infrastructure.
  - The 100-event cap is hit.
  - The board needs live counts before M5 exists.

### D-011 Frontend shell: tooling, generated client, and token handling (DRAFT)
- **Date:** 2026-11-09
- **Context:** M0.7 starts the frontend. It needs a typed client for the API whose contract is the
  committed `docs/openapi.json` (D-010), an auth layer that works with strict refresh-token reuse
  detection (D-008), and tooling that won't fight the custom design planned for M5 (PRD 7).
- **Options considered:**
  - Package manager: npm; pnpm.
  - Client generator: openapi-typescript + openapi-fetch (types only, tiny runtime); orval (generates
    TanStack Query hooks and mocks); @hey-api/openapi-ts (0.x, frequent breaking changes);
    openapi-generator (Java, verbose).
  - Generated client: committed with a regenerate-and-compare check; generated at build time.
  - Router: React Router; TanStack Router (type-safe params, more concepts); wouter (minimal).
  - Data fetching: TanStack Query; plain fetch in useEffect.
  - Styling: CSS Modules + CSS variables; Tailwind; a component library (conflicts with PRD 7).
  - Tests: Vitest + React Testing Library + jsdom + MSW; the same with hand-stubbed fetch.
  - URL scheme: app pages separate from API prefixes; the API behind `/api` with a proxy rewrite.
- **Decision:**
  - **Tools:** npm; openapi-typescript + openapi-fetch; React Router (library mode); TanStack Query;
    CSS Modules + `src/styles/tokens.css`; Vitest + React Testing Library + jsdom + MSW, with
    Playwright from M1.8.
  - **Generated types:** `src/api/schema.d.ts` is committed. `npm run gen:api` writes it and
    `npm run check:api` regenerates in memory and fails on a difference (CI in M0.8). Both use one
    script, so the check compares exactly what generation would write.
  - **Auth:** the access token lives only in memory. Our own `authFetch` (passed to openapi-fetch)
    adds the bearer token. On a 401 outside /auth, it refreshes once and retries once. Concurrent
    401s share one in-flight refresh, and a request whose token was already replaced retries without
    refreshing. Refreshes are serialised across tabs with the Web Locks API (`navigator.locks`),
    falling back to per-tab only where it is missing. Refresh and logout send `X-Requested-With`.
    Errors become `ApiError`, whose `code` is the generated union of codes.
  - **Clock:** countdowns use `offset = serverTime − midpoint(sent, received)`.
  - **URLs:** app pages are `/` and `/drops/:id`. The Vite dev proxy forwards only /auth, /events,
    /actuator and /v3, so the API and refresh cookie are same-origin.
  - **TypeScript is pinned to 5.9.3**, not 7.0. typescript-eslint 8.72 supports TypeScript
    `<6.1.0` and openapi-typescript 7.13 only `^5.x`, so npm can't install them alongside 7.
    **Revisit** when both support TypeScript 7.
  - **Supply chain:** exact versions only (`save-exact=true` in `.npmrc`). Every version is
    published at least 14 days before install, and `npm install --before=<date>` applies the same
    cutoff to transitive dependencies. package-lock.json is committed.
  - No login UI yet. It comes with the first page that needs a user (M1.8).
  - **Session (added in M1.8b):** `api/auth.ts` also keeps a session status (`restoring`,
    `loggedIn`, `loggedOut`) that follows the token. On page load, one memoized refresh restores the
    session (the cookie survives a reload, the in-memory token doesn't); any failure means logged out,
    shown without an error. Pages that need a user wait while restoring, so a reload doesn't bounce
    to /login. `?next=` after login accepts only in-app paths (no open redirect).
- **Why:**
  - **openapi-typescript:** generates only types, so the committed diff stays small and readable,
    and our auth logic is plain code we own rather than generator output.
  - **TanStack Query:** handles caching, ignoring stale responses, and refetching, which the board
    needs later anyway.
  - **CSS Modules + tokens:** no dependency, and M5 builds on the PRD 7 tokens directly.
  - **MSW:** tests run the real client code against fake responses. Unhandled requests fail the test
    explicitly; MSW's own 'error' mode only makes the fetch fail, which the UI can swallow.
  - **Shared and cross-tab refresh:** strict reuse detection (D-008) turns any two concurrent
    refreshes with the same cookie into a logout, so refreshes must queue both within a tab and
    across tabs.
  - **Separate app and API URLs:** a page reload never lands on the API, and the cookie path
    (`/auth`) needs no rewriting.
- **Trade-offs:**
  - Hooks are written by hand (one line each).
  - Exact pins and the 14-day rule mean security fixes arrive at least 14 days late. On 2026-11-09,
    `npm audit` reports 10 moderate findings from one advisory (minimatch, GHSA-g3hv-75wg-m249) in
    lint tooling only. `npm audit --omit=dev` reports 0. The fix (minimatch 11.0.1, published
    2026-10-27) wasn't 14 days old yet.

- **Date:** 2026-11-09
- **Context:** The M0 exit criterion needs `docker compose up` to run the system on a clean clone.

  - The frontend stays on `npm run dev` (Vercel in M7.1).

### D-014 Seat state machine: shape, owner pointers, and jqwik (DRAFT)
- **Date:** 2026-11-10
- **Context:** M1.1 turns PRD 2's seat diagram into code (the guard D-004 put in code). The PRD
  leaves some things open: refund (SOLD to AVAILABLE) is drawn but marked P2, the database CHECK
  allows more pointer shapes than any transition needs, and it doesn't say what happens to
  `hold_id` once a seat is sold. Property tests need a new test dependency.
- **Options considered:**
  - Shape: a mutable entity; an immutable record whose transitions return a new seat.
  - SOLD: final; leaves SOLD through refund.
  - `hold_id` on sell: kept (a trail from seat to hold); cleared.
  - Property testing: jqwik 1.9.2, 1.9.3, 1.10.x; hand-rolled random loops in JUnit.
- **Decision:**
  - `inventory.seat.EventSeat`, an immutable record, internal to inventory (D-007): only inventory
    writes `event_seats`. Transitions: `hold` (AVAILABLE to HELD), `release`, `expire`, `failSaga`
    (HELD to AVAILABLE, the caller's hold must own the seat) and `sell` (HELD to SOLD, same check).
    Everything else throws `IllegalSeatTransitionException` with a reason (WRONG_STATE or
    HOLD_MISMATCH). It has no HTTP meaning; the inventory service maps it to SEAT_TAKEN or
    HOLD_EXPIRED when those endpoints exist (M1.4/M1.5).
  - The constructor enforces exactly `ck_event_seats_status_pointers`, so any row the database
    accepts can be loaded. Transitions only produce the strict shape: **the pointer on a seat is its
    current owner** (the hold while HELD, the order once SOLD). `sell` clears `hold_id`; history
    stays in `holds.seat_ids` and `order_items`.
  - **SOLD is final.** Refunding a sold seat is left out; adding it needs its own decision, and the
    "SOLD never goes back" property test would change to "only through refund". A payment that
    succeeds after its hold expired (PRD 6.4) refunds money but never touches a SOLD seat.
  - Every successful transition bumps `version` by 1 (the optimistic strategy compares it, M2.1).
  - Repeated or racing calls (expire after release) are rejected, not treated as no-ops.
  - Test dependency: `net.jqwik:jqwik:1.9.2`.
- **Why:** An immutable record can't be left half-changed by a rejected transition, and its
  constructor makes an invalid seat impossible to build. Clearing `hold_id` keeps "who owns this
  seat?" to one column per state, and stops it from quietly answering M1.5's open "how does an order
  link to its hold" question. jqwik 1.9.2 is built against JUnit Platform 1.11.3, older than the
  1.12.2 that Boot 3.5's BOM pins, so it runs on a newer platform (backwards compatible). 1.9.3 and
  1.10.x target Platform 1.13 and 1.14 and would be forced down to 1.12.2, which risks
  `NoSuchMethodError` at runtime. 1.9.3 only added a Kotlin API change. The trade-off of the guard
  in code (D-004) remains: the optimistic and Lua strategies repeat these rules in a WHERE clause or
  in Lua, and this class is the reference they must agree with.
- **How I'd know it was wrong:** refunds or seat kills become real requirements and SOLD can't stay
  final; or debugging keeps needing "which hold did this sold seat come from?" without joining
  `holds`; or a JUnit upgrade (Boot 4) leaves jqwik 1.9.2 behind, at which point move to 1.10.x.

### D-015 InventoryStrategy interface and one lock order (DRAFT)
- **Date:** 2026-11-10
- **Context:** PRD 6.2 needs three interchangeable strategies (pessimistic, optimistic, Redis-first)
  behind one interface. The Redis-first Lua script creates a hold before Postgres knows about it,
  and `event_seats.hold_id` has a foreign key to `holds`, so whoever creates the hold must insert the
  hold row. Several code paths will lock the same rows (hold, release, the expiry sweeper, the
  allowance counter from D-005, sell in M1.5), and two paths that lock in different orders can
  deadlock.
- **Options considered:**
  - Hold id: generated by the strategy; generated by the caller.
  - Results: exceptions for "seat taken"; sealed outcome values.
  - Expiry: the caller passes an `Instant`; the caller passes a `Duration` and the strategy computes
    the expiry from its own clock.
  - Lock order: sort ids in Java and lock in that order; let Postgres sort inside the locking
    statement (`ORDER BY seat_id FOR UPDATE`).
- **Decision:**
  - `inventory.strategy.InventoryStrategy` (internal, D-007): `hold(HoldRequest)` returns
    `Held(holdId, seatIds, expiresAt)` or `Rejected(SEAT_TAKEN | UNKNOWN_SEAT, offending seatIds)`;
    `release(eventId, holdId, reason)` returns `Released`, `NotActive`, `NotExpired` or `NotFound`.
    UNKNOWN_SEAT (a seat not in this event) takes precedence over SEAT_TAKEN. Exceptions are only for
    bugs and infrastructure failures.
  - The caller (the hold service, M1.4) generates a **new** `holdId` for every attempt (D-002). Reusing
    one is a programming error: the `holds` primary key rejects it with an exception and the
    transaction rolls back. Retrying the same buyer action safely is the job of an idempotency key at
    the API, not of the strategy.
  - `HoldRequest` rejects an empty list, duplicate seat ids and a `holdFor` under 1 s, so no strategy
    can forget those checks.
  - `HoldRequest` carries `Duration holdFor`. Each strategy computes the expiry from its own
    authoritative clock: Postgres `now()` for pessimistic and optimistic, Redis `TIME` for Lua. The
    database clock is authoritative for hold expiry; app servers' clocks are not. `now()` (the
    transaction's start time), not `statement_timestamp()`: time spent waiting for a seat lock comes
    off the hold, but row locks are released at commit, so a buyer only ever waits for another
    in-flight transaction (milliseconds), never for another buyer's 5-minute hold (a HELD seat is
    rejected at once). The cost is negligible, and `now()` keeps `expires_at - created_at` exactly the
    hold duration. If M2.4 shows long lock queues on hot seats, that is the `lock_timeout` question
    below, not a reason to change the clock.
  - `release(…, EXPIRED)` re-checks `expires_at <= now()` after locking the hold row and returns
    `NotExpired` otherwise: the sweeper picks holds before it has the lock, and a hold extended in
    between (PRD 6.3) must survive.
  - Both methods are `@Transactional` with the default REQUIRED propagation, so a caller that is
    already in a transaction pulls them into it. Callers must not do that: the sweeper and the hold
    service call the strategy from outside any transaction, one hold per call. (Joining several holds
    in one transaction would break the lock order below, and one failure would roll back all of them.)
  - The strategy inserts the `holds` row in the same transaction as the seat updates.
  - **Lock order, for every code path:** (1) the hold row, when the path starts from an existing hold
    (release, expiry, sell); (2) the event seats, in Postgres `seat_id` order, taken by one
    `SELECT … ORDER BY seat_id FOR UPDATE`; (3) the user's allowance row (M1.4). Creating a hold never
    waits on an existing hold row. The sweeper releases one hold per transaction. (M2.3a, D-023: the
    strategy switch takes the event row `FOR NO KEY UPDATE` and then every seat of the event in this
    order; no other path locks event rows.)
  - Seat UPDATEs add `AND version = :oldVersion`; zero rows updated under the lock is a bug and
    throws. (Measured: with `FOR UPDATE` removed, this check alone turned every double-hold in the race
    tests into a rollback; with both removed, two buyers were told `Held` for the same seat.)
- **Why:**
  - Caller-generated ids and outcome values fit all three strategies: Lua returns a status code, not
    an exception, and "seat taken" is the normal result under contention.
  - A duration keeps two clocks out of one rule: if app servers computed expiry, clock skew between
    them would shorten or lengthen holds.
  - Postgres does the sort because the order that matters is the order rows are locked in, and that
    is Postgres's order. Java's `UUID.compareTo` compares signed longs and disagrees with Postgres's
    unsigned byte order (checked on Java 21 and Postgres 16: `9000…` sorts first in Java and last in
    Postgres). A Java sort followed by one `IN (…) FOR UPDATE` changes nothing: Postgres locks rows
    in the order its scan returns them, not the order of the IN list. Without `ORDER BY` that scan
    order is the physical or index order, which happens to be consistent but is not a rule anyone
    wrote down (the lock-order test stores rows out of `seat_id` order and fails without `ORDER BY`).
    Mixing a Java order in one path with `ORDER BY` in another is two orders, which can deadlock.
  - Locking several holds in one sweeper transaction would take seat locks hold by hold, not in one
    global seat order.
- **How I'd know it was wrong:** M1.3 or the k6 runs log deadlocks (`40P01`); or holds expire at
  visibly different times on different instances; or the optimistic strategy needs a third
  rejection the interface can't express (I'd add `CONTENDED` then); or under a drop, buyers queueing
  on one hot seat's lock use up the connection pool and stall other events (then add a bounded
  `lock_timeout` returning a rejection; measured in M2.4).

### D-016 Holds API, per-user cap in the strategy, expiry sweeper (DRAFT)
- **Date:** 2026-11-10
- **Context:** M1.4 puts holds behind HTTP: create (all-or-nothing, with the D-005 cap), cancel, and
  expiry after five minutes (PRD 6.3). PRD 10 names SEAT_TAKEN (with `takenAgoMs`), LIMIT_EXCEEDED
  and HOLD_EXPIRED but gives no statuses for most of them, the schema records no "taken at" time on
  a seat, D-015 gives every attempt a new hold id (so a retried POST can't be recognised by id), and
  the app will run as several instances (M6.1), each of which could sweep.
- **Options considered:**
  - `takenAgoMs`: a new `event_seats.status_changed_at` column; the owner's `created_at` read in the
    strategy's transaction; the same read after the transaction; null until M5.3.
  - Sweeper with several instances: every instance sweeps and duplicates are tolerated;
    `FOR UPDATE SKIP LOCKED` claims; ShedLock (new dependency and table); a Postgres advisory lock.
    Interval 1 s, 5 s or 30 s.
  - Retried POST after a timeout: accept SEAT_TAKEN; return the caller's existing hold if it covers
    exactly the requested seats; an `Idempotency-Key` now (pulled forward from M3.1).
  - Statuses: HOLD_EXPIRED 410 / 409 / 422; someone else's hold 404 / 403; own released or expired
    hold 204 / 410; own converted hold 409 / 404.
  - Where the cap is checked: in the hold service before the strategy; inside the strategy's
    transaction.
- **Decision:**
  - The cap lives **inside the strategy's transaction** (CLAUDE.md: enforced in every strategy).
    Step 4b, after the seat decision and before the hold insert, is one upsert:
    `INSERT … SELECT … WHERE :n <= per_user_limit ON CONFLICT DO UPDATE SET used = used + n WHERE
    used + n <= per_user_limit`. Zero rows = `Rejected(LIMIT_EXCEEDED)` with nothing written.
    Precedence UNKNOWN_SEAT > SEAT_TAKEN > LIMIT_EXCEEDED. The limit is read in that same statement.
  - Every release reason (RELEASED, EXPIRED, SAGA_FAILED) gives the seats back as step 11b, after
    the seat writes (lock order hold, seats, allowance; D-015). CONVERTED never reaches release, so
    bought seats keep counting. A missing row or a decrement below zero throws and rolls back.
  - `takenAgoMs`: the most recent owner's `created_at` (the hold if HELD, the order if SOLD),
    computed in SQL against `clock_timestamp()` while the seats are still locked. `Rejected` gains a
    `takenAgoMs` field, set exactly for SEAT_TAKEN.
  - Sweeper: **every instance sweeps**, fixed delay 5 s, each expired hold released in its own
    transaction through `release(…, EXPIRED)`. Candidates are read in pages of 500, oldest first,
    with keyset paging on `(expires_at, id)`, so holds whose release keeps failing (drift, which
    release refuses to touch) can't fill every page and starve healthy holds behind them (found by
    the correctness review). Neither the sweeper nor the hold service is `@Transactional`.
    `stampede.holds.sweeper.enabled/interval/batch-size`. SKIP LOCKED is the noted optimisation if
    duplicate work ever shows up (M6.1).
  - Retry: on SEAT_TAKEN, if the caller has an ACTIVE, unexpired hold on **exactly** the requested
    seats (array containment both ways), return it with 200 instead. M3.1 considers an
    `Idempotency-Key` for this endpoint too.
  - Statuses and codes: SEAT_TAKEN, LIMIT_EXCEEDED (with `limit`), SALE_NOT_OPEN and HOLD_CONVERTED
    are 409; HOLD_NOT_FOUND 404, for unknown ids and someone else's hold alike (no IDOR, no
    existence probe); DELETE of your own RELEASED or EXPIRED hold is 204 (idempotent); unknown seat
    ids are 400 VALIDATION_FAILED with a `seatIds` field error. HOLD_EXPIRED is **410 Gone**, added
    to `ErrorCode` in M1.5, the first task that returns it.
  - Sale window: holds only when `drop_at <= now()` and the event is SCHEDULED or LIVE; otherwise
    409 SALE_NOT_OPEN; DRAFT is 404 like GET /events/{id}. Checked by the service before the
    strategy, unlocked. Dev-only profile `demo-open-sale` sets the demo drop to one minute ago (and
    the start to its seed offset from now) so the demo can be held locally and by the M1.8 seat map.
  - Admission (M4.2): the controller will require an `X-Admission-Token` header verified through
    `waitingroom::api` (already an allowed dependency) before calling the service; 403 NOT_ADMITTED.
    Not in the spec until it is enforced.
- **Why:**
  - A cap checked outside the strategy's transaction is the race D-005 exists to prevent. The upsert
    also covers the user's first hold, before any counter row exists: when two first requests race,
    Postgres makes the second wait for the first insert and then takes the DO UPDATE path with its
    WHERE re-checked against the committed value.
  - Reading `created_at` needs no migration and no extra write on the hot path. The read happens only
    when a hold is rejected, under seat locks that keep the owner pointers stable, and reads (not
    locks) the hold or order row, so the lock order is untouched. `clock_timestamp()` because the
    owner may have committed after this transaction's `now()`.
  - Duplicate sweeping is already proven safe (`cancelAndExpiryOfTheSameHoldTakeTurns`, and
    `twoSweepersAtOnceExpireEveryHoldExactlyOnce`), costs no code or dependency, and the sweeper is
    the safety net behind Redis expiry (M2.2), so 5 s of lateness is fine.
  - Matching on the exact seat set fixes the common retry case with one read on the rejection path
    and no table. A deliberate duplicate request also gets the existing hold, which is harmless.
  - 404 for someone else's hold reveals nothing; 204 for an already-ended own hold matches what the
    caller wanted (not holding the seats); a converted hold is a real conflict the client must see.
- **Known limits (correctness review, accepted for now):** the sale-window and strategy read is
  unlocked, so a hold can commit just after an admin pauses the event, and once M2.3 lets an event
  change strategy, two requests could briefly use different strategies (re-check inside the
  strategy transaction then, e.g. in the upsert's SELECT on events). **M2.3a (D-023):** every strategy
  now re-checks strategy and sale window inside its transaction after its first seat lock
  (`StrategyChanged`). That makes the strategy switch airtight; the pause race is only narrowed until
  the M5.5 pause locks the seats too. `takenAgoMs` for a SOLD seat
  is the order's creation time, not the moment it was sold. The `limit` in LIMIT_EXCEEDED comes from
  the unlocked pre-read. I8 treats `used > per_user_limit` as drift, which is wrong if an admin ever
  lowers a limit below existing holds. The in-flight retry (second POST waiting on the first's seat
  locks) is correct by reasoning but not tested.
- **How I'd know it was wrong:** I8 (allowance vs active holds) fires in the harness or the M1.7
  checker; the sweeper logs the same failed hold every tick (a drifted counter); multi-instance runs
  (M6.1) show lock waits on hold rows from duplicate sweeps; clients retrying with a *different*
  seat set double-hold, which needs the M3.1 idempotency key; or the unlocked sale-window check lets
  holds through on a paused event often enough to matter (move it into the strategy).

### D-017 Orders from holds: synchronous checkout in saga-shaped steps (DRAFT)
- **Date:** 2026-11-10
- **Context:** M1.5 turns an ACTIVE hold into a PAID order with a fake payment, before the M3 saga
  exists. `orders` had no link to its hold (M0.2 note). D-015 says strategy callers must not be

    sale separately.
  - `event_seats.order_id`: set only on sell; attached at order creation while the seat is HELD.
  - Idempotency-Key: wait for M3.1 and let the unique hold link make retries safe (loser gets 200
    with the existing order, or 409); require it now with the full PRD 6.4 semantics.
  - Fake payment: always succeeds; always succeeds and tests swap the provider bean; a config switch.
- **Decision:**
  - **V3 adds `orders.hold_id uuid NOT NULL`**, `fk_orders_hold (hold_id, event_id) → holds (id,
    event_id)` and `uq_orders_hold UNIQUE (hold_id)`. One hold has at most one order, ever (a
    cancelled order's hold is never reused: every hold attempt has a new id, D-015).
  - **One transaction per step**, in the order of the PRD 6.4 saga. The orchestrator
    `booking.checkout.CheckoutService` is not `@Transactional`:

    | Step | Owner (through its api) | Transaction | What it does |
    |---|---|---|---|
    | 0 HoldVerified | `inventory::api` `HoldService.checkoutHold` | none, unlocked read | caller's hold? ACTIVE and `expires_at > now()`? seat prices from the tiers |
    | 1 OrderCreated | booking `OrderWriter.createPending` | booking's own | PENDING order + active items; `uq_orders_hold` decides a race |
    | 2 Payment | `payments::api` `PaymentService.charge` | statement-level; provider call outside any transaction | payment row CREATED first, then SUCCEEDED or FAILED |
    | 3 SeatsSold | `inventory::api` `HoldService.sellForOrder` → `InventoryStrategy.sell` | the strategy's | lock hold row, re-check ACTIVE and not expired, lock seats `ORDER BY seat_id`, `EventSeat.sell`, hold CONVERTED; allowance untouched |
    | 4 PAID | booking `OrderWriter.markPaid` | booking's own | guarded PENDING → PAID, saga_state SEATS_SOLD; idempotent |

  - **`event_seats.order_id` is set only on sell** (D-014's strict shape stays: the pointer is the
    current owner). During PENDING the link is `orders.hold_id` plus `order_items`. A HELD seat
    never carries an order id, so "sell overwrites another order's pointer" can't happen; `sell` of a
    seat held by another hold is rejected by `EventSeat` (HOLD_MISMATCH).
  - **No Idempotency-Key until M3.1 (a deliberate deviation from PRD 10).** A concurrent `POST /orders`
    for the same hold, or a retry after a successful one, gets **200 with the existing order** as it
    is now (possibly still PENDING), instead of a second order or charge. A retry after a checkout that
    *failed* gets 410 HOLD_EXPIRED, because the failure released the hold (step 0 sees it RELEASED).
  - **Fake payment:** `payments.provider.PaymentProvider` (interface), `FakePaymentProvider` always
    succeeds. Tests use `@MockitoSpyBean` to decline or throw. A decline is 402 PAYMENT_FAILED: order
    CANCELLED, hold released with reason SAGA_FAILED (new `HoldService.releaseForFailedCheckout`).
  - **Status guards:** `OrderStatus` (PENDING → PAID/CANCELLED) and `PaymentStatus` (CREATED →
    SUCCEEDED/FAILED, SUCCEEDED → REFUNDED) are checked in code, and each UPDATE repeats the expected
    status in its WHERE clause.
  - **Errors:** HOLD_NOT_FOUND 404 (also for someone else's hold), HOLD_EXPIRED 410, PAYMENT_FAILED
    402, SEAT_TAKEN 409 (a seat still in another order's active items), ORDER_NOT_FOUND 404 (also for
    someone else's order). An unexpected failure is 500 INTERNAL_ERROR after compensation.
  - **Compensation in the orchestrator, best effort.** After step 1 every exit must leave the order
    PAID or CANCELLED. Compensation releases the hold **first**: that release takes the hold row
    lock, the same lock the sale takes, so its answer is definitive. If the hold is CONVERTED, the
    sale committed and the order is finished instead of undone. Then the order is cancelled (items
    inactive, which unblocks the seats), then the payment refunded. Each step is tried even if
    another fails; failures are logged with the order id and attached to the original exception.

    | Failure | Order ends | Seats / hold | Money | Response |
    |---|---|---|---|---|
    | Step 0 says not found / expired / converted | no new order | unchanged | none | 404 / 410 / 200 existing order |
    | Step 0 or 1 throws | nothing written (step 1 rolls back) | unchanged | none | 500 |
    | Step 1 hits `uq_orders_hold` | the other request's order | unchanged | none | 200 existing order |
    | Step 1 hits `uq_order_items_active_seat` | no new order | unchanged (blocked by another checkout: in flight, or crashed) | none | 409 SEAT_TAKEN ("try again shortly") |
    | Step 2 declined | CANCELLED | hold RELEASED, seats AVAILABLE, allowance back | payment FAILED | 402 (500 if the compensating release throws: the 402 promises released seats) |
    | Step 2 throws | CANCELLED | hold RELEASED, seats AVAILABLE, allowance back | payment left CREATED: outcome unknown, for M3 reconciliation | 500 |
    | Step 3 says hold expired / released | CANCELLED | nothing sold; an ACTIVE-but-expired hold is left to the sweeper | REFUNDED | 410 |
    | Step 3 throws, sale rolled back | CANCELLED | hold RELEASED, seats AVAILABLE, allowance back | REFUNDED | 500 |
    | Step 3 throws, sale had committed | PAID (finished) | SOLD, hold CONVERTED | kept | 201 |
    | Step 4 throws, then succeeds on retry (3 attempts) | PAID | SOLD | kept | 201 |
    | Step 4 fails every attempt | **PENDING** | SOLD to it, hold CONVERTED | kept | 500 |
    | The compensating release throws | **PENDING** (not cancelled, not refunded) | unknown | kept | 500 |
    | A compensating cancel or refund throws | the other steps still run; logged | | | 500 / original |

    Once seats are sold, nothing is ever released or refunded: undoing a sale would refund a buyer
    who keeps seats, or leave SOLD seats without a PAID order. The two **PENDING** rows are the safe
    side of an unknown: the seats are not lost (or the order isn't refunded by mistake), only the
    order status is wrong, and the M1.7 invariant checker reports it.
  - Invariant I8 now counts the seats of ACTIVE **and CONVERTED** holds: a converted hold's seats
    are exactly its order's, and counting holds (not order items) avoids counting a seat twice while
    its order is PENDING and its hold still ACTIVE.
- **Why:**
  - A unique constraint is the simplest correct referee for "two requests, one hold": both pass the
    check in Java, Postgres lets one row commit and fails the other. No lock taken by hand.
  - Step-per-transaction keeps D-015 (the strategy owns its transaction and the hold → seats lock
    order), works for Redis, never holds a transaction open across the provider call, and is exactly
    the step list the M3 saga will persist. Step 1 must commit before step 3 anyway, because
    `event_seats.order_id` has a foreign key to `orders`.
  - Setting `order_id` only on sell needs no new transition, no extra inventory call and nothing new
    in Lua.
  - The unique hold link already makes a retry safe; building the general idempotency table here
    would be M3.1 pulled forward.
  - A provider swapped in tests keeps the main code free of a fail switch that the M3 chaos
    provider replaces anyway.
  - `sell` checks `expires_at > now()` under the hold lock, not just `status = 'ACTIVE'`: the sweeper
    runs every 5 s, so an ACTIVE hold can be past its expiry, and status alone would sell it.
- **Known limits (until M3):**
  - **A real process crash between steps** leaves a PENDING order: its active items keep its seats
    from every other order (409 SEAT_TAKEN), even after the sweeper frees the hold. No code here can
    run after a crash; M3's persisted saga resumes or compensates it.
  - The two PENDING rows of the failure table (step 4 never succeeds; the compensating release
    throws) end the same way.
  - **An unknown payment outcome stays CREATED** and is never closed here: the provider threw, or it
    succeeded and recording that failed (money moved, and its `provider_ref` may be lost). Closing it
    as FAILED could lose a real charge (found by the correctness review). M3's reconciliation asks
    the provider by payment id, which is the provider's idempotency key.
  - **An in-flight checkout blocks the seats for its duration.** Step 0 is an unlocked read and step 1
    doesn't re-check the hold, so a checkout whose hold ends while it pays keeps active items until
    step 3 cancels it; another buyer who holds those seats meanwhile gets 409 SEAT_TAKEN ("try again
    shortly"). Seconds with the synchronous fake provider; with M3's asynchronous payment it can be
    minutes, so M3 should re-check the hold in step 1 or order the seats' release after cancellation.
  - The step 4 retries are immediate, without backoff. Only `RuntimeException` is compensated; an
    `Error` (OutOfMemoryError, StackOverflowError) after step 1 ends like a crash.
  - SEAT_TAKEN on POST /orders lists all the hold's seats, not only the blocked ones. The constraint
    is recognised by its name in the Postgres message (the driver is runtime-only, so
    `PSQLException.getServerErrorMessage().getConstraint()` isn't available at compile time).
  - POST /orders doesn't check the event's status (paused or cancelled), like D-016's unlocked
    sale-window check.
  - `DELETE /holds/{id}` during an in-flight checkout still releases the hold; that checkout then
    refunds and answers 410.
  - No Idempotency-Key, so a retry that sends a **different** hold id is a new order (it is a
    different hold, so this is the caller's real intent or a client bug, not a double charge).
- **How I'd know it was wrong:** the M1.7 checker finds PENDING orders or SOLD seats without a PAID
  order outside a known crash; buyers see SEAT_TAKEN on seats that look free (crashed checkouts are
  more common than assumed, so M3 recovery is needed sooner); M2.4 load runs show `uq_orders_hold`
  violations from something other than double clicks; or M3's saga can't reuse these steps as they
  are.

### D-018 Signed tickets: JDK Ed25519, compact payload, issued after PAID (DRAFT)
- **Date:** 2026-11-10
- **Context:** M1.6 issues the tickets of a PAID order as the saga's TicketsIssued step (PRD 6.4)
  and signs them so a gate scanner can verify them offline with only a public key (PRD 6.9). Three
  choices were open: how to sign and encode the payload (a smaller payload is an easier QR code to
  scan), what happens when issuing fails after the order is already PAID (D-017: a sale is never
  undone), and what "holder" means in a payload anyone can read. Ticketing may not read inventory's
  or booking's tables (D-007), yet the wallet should show "Section A, Row 3, Seat 5".
- **Options considered:**
  - Signing: the JDK's built-in Ed25519; BouncyCastle (`bcprov-jdk18on`); Nimbus JOSE (already on
    the classpath) for a JWS, which needs Google Tink for Ed25519.
  - Payload: a compact binary format in base64url (195 characters); a hand-built JWS (about 400).
  - Issuing fails after PAID: retry, then keep PAID and answer 201; the same but answer 500; issue
    in the transaction that marks the order PAID.
  - Holder: the user id; a per-ticket HMAC of the user id; the name or email.
  - Seat labels: ids only (the frontend resolves labels); booking passes labels and ticketing keeps a
    snapshot.
- **Decision:**
  - **JDK Ed25519, no new dependency.** The key in the environment is the 32-byte seed
    (`STAMPEDE_TICKET_SIGNING_KEY`, base64), which PowerShell can generate. The JDK has no public
    "seed to public key" method, so `Ed25519Keys` hands the JDK key generator a random source that
    returns the seed, then checks that the private key it got back contains that seed. The signer
    signs and verifies a test message at startup, and `Ed25519KeysTest` checks the RFC 8032 vector.
    A missing, malformed or wrongly sized key (exactly 32 bytes) stops the app at startup.
  - **Compact binary payload, format 1:** format byte, 4-byte key id, ticket, event, seat and holder
    UUIDs, issue time in epoch seconds, version: 81 bytes, signed, then
    `base64url(payload).base64url(signature)`, 195 characters. Specified in docs/ticket-format.md
    with a test vector. The verifier accepts only the canonical text (no padding, unused bits zero),
    so each ticket has exactly one valid string.
  - **Key id derived, not configured:** the first 4 bytes of SHA-256 over the raw public key. Stored
    on each ticket (V4 `tickets.key_id`) and published as `kid` by `GET /tickets/keys` (public, a
    JWKS with one OKP key today), so rotation can later publish several keys.
  - **Step 5 after step 4, as one booking transaction** (`booking.checkout.TicketStep`): lock the
    order row (`FOR NO KEY UPDATE`), require PAID/SEATS_SOLD (TICKETS_ISSUED means done), require the
    seats to be exactly the order's active items, call `ticketing::api` `TicketIssuer.issueForOrder`
    (its transaction joins), then record saga state TICKETS_ISSUED. The check, the tickets and the
    saga state commit together, so no refund (M3) can slip in between "still PAID?" and "issue",
    and TICKETS_ISSUED never exists without tickets. Three attempts. If all fail, the order stays **PAID at SEATS_SOLD**,
    the answer is still **201**, and an error is logged; nothing is released or refunded. A retried
    `POST /orders` for the same hold (hold CONVERTED) re-runs issuing before answering 200.
  - **Idempotent by the database:** each insert is `ON CONFLICT (event_id, seat_id) WHERE status <>
    'REVOKED' DO NOTHING` on `uq_tickets_live_seat`, in one transaction with seats in id order;
    afterwards every seat's live ticket must belong to this order, or the whole issue rolls back
    and throws.
  - **Holder = user id only.** No personal data in a readable QR code.
  - **Seat labels as a snapshot** (V4 `section_code`, `row_label`, `seat_number`), passed by booking
    from inventory's checkout data (`CheckoutHold.CheckoutSeat`). Not signed: the scanner trusts the
    seat id, the label is for display. `GET /me/tickets` rebuilds the QR string from the stored row
    and signature; it never signs.
  - `issued_at` is whole seconds, set in Java, so the row holds exactly what was signed.
- **Why:**
  - The JDK does Ed25519 natively; one checked workaround is cheaper than an 8 MB library (or Tink)
    for one call. Ed25519 is deterministic, so no per-signature random nonce can go wrong.
  - 195 characters is roughly a 57×57 QR code at medium error correction, against roughly 81×81 for
    a JWS: fewer, larger dots scan more reliably from a phone screen in a queue. The cost is a format
    of our own, hence the spec and test vector.
  - After PAID the buyer has paid and has the seats; a 500 would call a successful purchase a
    failure, and the retry it invites returns the existing order anyway. Issuing in the PAID
    transaction would widen D-017's stuck-PENDING case for a failure that loses nothing.
  - The unique index already says "one live ticket per seat"; letting it decide races needs no lock
    taken by hand and keeps the guarantee even for callers that skip the Java checks.
- **Correctness review (2026-11-11):** no live bug found. Fixed from it: step 5 checked "PAID?" and
  issued in separate transactions (now one, under the order lock, with the seats checked against
  the order's items); the verifier accepted padded or non-canonical strings; the concurrency tests
  didn't prove two transactions overlapped (now one holds its transaction open and the second is
  seen waiting in `pg_locks`), didn't race two orders for one seat, and ignored
  `-Dstampede.harness.rounds`; the test invariants didn't check PRD 6.10's "every paid order has
  issued tickets" (now rule T3, which the step-5 failure test expects to be violated).
- **Known limits:**
  - A PAID order can be without tickets until its buyer retries or M3 recovery runs; the wallet is
    empty meanwhile, against PRD 6.10 invariant 3 ("every paid order has issued tickets") and the
    success metric "paid orders without issued tickets: 0". Nothing recovers it automatically before
    M3, and nothing tells the buyer: the 201 response carries no ticket or saga field, so a client
    that got 201 has no reason to retry. The M1.7 checker must report PAID orders still at
    SEATS_SOLD (T3, with a grace period for checkouts still in step 5).
  - **Trust boundary:** `TicketIssuer` (ticketing's api) checks only that no other order holds a
    live ticket for a seat. It cannot check that the order is PAID or that the seats are sold to it:
    those live in booking's `orders` and inventory's `event_seats`, which ticketing may not read
    (D-007). `TicketStep` makes those checks for the checkout; any future caller of `TicketIssuer`
    (control, M5) must make them too, or it can sign a valid ticket for an unsold seat, whose real
    buyer's step 5 would then fail every attempt.
  - The concurrency tests have no randomness, so `-Dstampede.harness.seed` doesn't apply to them;
    the two-order race alternates a 5 ms head start to make both orders win.
  - One key, no rotation yet: changing `STAMPEDE_TICKET_SIGNING_KEY` makes earlier tickets fail to
    verify. Rotation means keeping old public keys in the key set (and in `TicketVerifier`).
  - The signing key is a plain environment variable, like the JWT secret; no HSM or KMS.
  - The signature proves authenticity, not current validity: a screenshot of a valid QR scans as
    valid until check-in records it (PRD's rotating QR is a stretch goal).
  - Seat labels are a snapshot; renaming a section after issue isn't reflected (seat labels don't
    change after seeding today).
  - Saga state is guarded by WHERE clauses in `OrderWriter`, not yet by a saga state machine class
    (M3 persists the saga).
- **How I'd know it was wrong:** a JDK upgrade fails the RFC 8032 test or startup self-test (then
  move to a library); gate scanners struggle to read the codes (then a smaller encoding such as
  base45 in alphanumeric mode); the checker often finds PAID orders without tickets (then issue
  asynchronously from an outbox event, M3); or a scanner vendor needs a standard format (then JWS
  or CWT).

### D-019 Invariant checker v1: SQL rules in control, strict after every test, graced while running (DRAFT)
- **Date:** 2026-11-11
- **Context:** PRD 6.10 asks for an invariant checker that "runs continuously during operation and
  as a hard assertion after every test". By M1.6 the rules lived only in tests (`HoldInvariants`,
  `CheckoutTestSupport`) and ran only where a test remembered to call them. The checkout runs one
  transaction per step (D-017), so some impossible-looking states are briefly legitimate while it
  runs. Several tests leave broken data on purpose. Every rule joins tables owned by different
  modules, which D-007's table-ownership convention forbids.
- **Options considered:**
  - After-test wiring: a Spring `TestExecutionListener` registered in `META-INF/spring.factories`;
    a JUnit extension auto-detected for every test; a base class or `@ExtendWith` per test class.
  - Opting out: an annotation that names the exact rules expected to fire; a plain skip.
  - Exposure: tests only until M5.5; plus a scheduled run (log + gauge); plus an admin endpoint.
  - Scope: rules per event (all events = a loop); one global query per rule.
  - I8 when an admin lowers a limit: keep `used > limit` strict and forbid lowering below current
    use; split I8 into a violation and a warning; drop the limit half (a weakened check, rejected).
  - O6, which the unique index makes impossible: drop the index in a rolled-back test transaction
    to show the rule fires; only show that the index refuses the state.
- **Decision:**
  - **`control.invariants.InvariantChecker`** runs a list of `InvariantCheck`s per event and returns
    `Violation(ruleId, ruleName, eventId, detail)`. Today they are the 16 `SqlRules`: I1-I3, I8
    (holds), V1 (venue match, M0.2 note), O1-O7 (orders), C1 (capacity), T1-T3 (tickets). PRD
    6.10's five rules are O6 and O1 (#1), C1 (#2), T3 (#3), O1 (#4); #5 (Redis) is an
    `InvariantCheck` that M2.2 adds to the list. Existing queries moved word for word; O1, O4, O5
    and T3 gained grace conditions, and V1, O6, O7 and C1 are new.
  - **One snapshot per event:** an event's rules run in one READ ONLY transaction at REPEATABLE READ,
    so all rules see the same committed moment and the checker can't write. Called inside an
    existing transaction, it joins it.
  - **Grace:** with a positive grace, the in-between states of a running checkout are excused while
    the order is younger than it: seats SOLD and hold CONVERTED with the order still PENDING (O1,
    O5), any PENDING order (O7), PAID without tickets (T3), CANCELLED with the charge not yet
    refunded (O4). Grace zero is strict and used by every test. Age is measured from
    `orders.created_at`, the only timestamp on orders.
  - **After every Spring test:** `testsupport.InvariantAssertionListener`, registered in
    `src/test/resources/META-INF/spring.factories`, runs every rule over every event, strictly, on
    the **committed** database, and fails the test on any violation. Without a test transaction it
    runs right after the test method, before the `@AfterEach` cleanup. Inside one, it runs after
    Spring rolls it back (listener order 3000, below `TransactionalTestExecutionListener`'s 4000;
    "after" callbacks run in reverse order). Checking earlier waits forever on the locks the open
    test transaction holds (found the hard way: a TRUNCATE in a test transaction deadlocked the
    suite), and joining it fails when the test aborted it on purpose. Every check sets a 10 s
    `lock_timeout`. `-Dstampede.invariants.after-test=report` writes
    `build/reports/invariants/after-test.txt` instead of failing.
  - **Opt-out:** `@ExpectInvariantViolations(rules, reason)` on the test method. The rules that fire
    must be exactly the listed ones; a blank reason, an unknown rule or a stale annotation (nothing
    fires) fails the test. 16 tests carry it: 3 documented D-017 PENDING outcomes
    (`CheckoutFailureTest`), 6 tests with deliberate drift that the code must refuse to touch, 6
    strategy unit tests that test step 3 alone (a bare PENDING order that step 4 never finishes),
    and `TicketsApiTest`'s simulated refund (revisit in M3). Five other flagged tests had
    half-built setups and were fixed instead.
  - **Scheduled run:** `InvariantMonitor` runs `stampede.invariants.monitor.interval` (30 s) after
    the previous check finished, on events that are neither DRAFT nor ENDED, with
    `stampede.invariants.monitor.grace` (30 s, must be positive). It logs violations at ERROR (the
    first 20 in detail) and sets the gauge `stampede.invariants.violations{rule}` to the latest
    count. Off in tests. No endpoint until M5.5.
  - **Table ownership:** the checker is the one recorded exception to D-007's convention. It reads
    inventory's, booking's, payments' and ticketing's tables directly, only in a read-only
    transaction, because its rules are joins across modules that no single module's API can answer.
    `control`'s package-info lists the tables it reads.
  - **I8 stays strict:** `used > per_user_limit` is always a violation. Any future way to change a
    limit (none exists: nothing writes `per_user_limit` after insert) must refuse to go below any
    user's current `used` (409), checked under the allowance row locks.
  - **The one exception to CLAUDE.md's "never drop or relax" rule for `uq_order_items_active_seat`:**
    `InvariantCheckerTest.o6SeatInTwoActiveOrdersWithTheUniqueIndexBypassed` drops it inside a
    transaction that is always rolled back, in that class's own throwaway database, and then
    asserts the index is back. Nowhere else: never in a migration or a shared test database.
    Why: O6 is PRD 6.10's first invariant, and a rule that has never been seen to fire may be a
    query that can't fire. The index makes the state impossible otherwise. Postgres DDL is
    transactional, so the rollback restores the index exactly.
  - The concurrency harness calls the checker (strict) after every round instead of its own copy;
    its outcome-based checks I4-I7 stay in the harness.
- **Why:**
  - A listener registered once can't be forgotten by a new test class. An exact-rules annotation
    documents a known broken state without hiding an unrelated one.
  - Strict in tests, graced at runtime: a test's requests have all returned, so nothing may be
    mid-checkout; a running app always has checkouts in flight.
  - Rules per event use the `event_id` indexes, cost nothing for other events' history, and group
    the way the control room will show them. Measured: a full check of a sold-out 2,000-seat event
    (500 PAID orders, 2,000 tickets) takes a median 83 ms; the slowest rule (T2) takes 12 ms.
  - Refusing to lower a limit below current use keeps I8 one simple rule instead of grandfathering.
- **Known limits:**
  - For a test inside a test transaction, the listener sees only what it left committed (nothing,
    after the rollback), not its in-transaction state; such tests (InvariantCheckerTest,
    InvariantMonitorTest) assert their own. The listener's test calls it with a mocked
    `TestContext`; no dedicated test shows that the after-rollback path catches something, only that
    the suite doesn't hang and the step-3 report found violations in such classes.
  - Grace is measured from order creation: a healthy checkout slower than 30 s (M3's asynchronous
    payment) would be reported; raise the grace or add an `updated_at` to orders then.
  - `/actuator/metrics` isn't exposed (only health), so today the gauge is visible only inside the
    app; the ERROR log repeats every 30 s while a violation lasts.
  - Not checked yet: ACTIVE holds long past their expiry, i.e. a stuck sweeper (PLAN.md, M1.7).
    Resolved in M2.2c-2: rule I9 (see the update below).
  - O6 and C1 are tripwires behind constraints and V1: C1 can't fire unless V1 or an index breaks
    first. O5 filters a FULL JOIN by `coalesce(event_id)`, which no index serves; fine at today's
    sizes (3 ms on the 2,000-seat event).
  - Modulith can't see that the checker only reads; the read-only transaction is what enforces it.
- **How I'd know it was wrong:** the monitor reports violations nobody can explain as a crash or a
  known limit (a rule is wrong, or the grace is too short); a test fails the after-test check only
  when run after another class (a leak between tests); the check takes long enough on a real event
  to matter (time it per event, then consider spreading rules over ticks); or the annotation list
  keeps growing (tests are building fake states instead of using the real paths).
- **Update 2026-11-14 (M2.2c-2, D-022):** two rules added, 18 in all. **I9** (SQL): an ACTIVE hold more
  than 2 minutes past its expiry, a stuck sweeper; the same threshold strict and graced. **I10**: PRD
  6.10 #5, "Redis hold state is consistent with Postgres", for REDIS_FIRST events loaded in Redis. It is
  not an `InvariantCheck` in the list: it reads Redis (through `inventory.api.RedisHoldState`) before the
  snapshot transaction starts, then compares inside it. `InvariantChecker`'s only public constructor
  now takes an `ObjectProvider<RedisHoldState>`; without a reader, I10 reports "cannot check" for every
  REDIS_FIRST event instead of passing. Annotations: `HoldExpirySweeperTest`'s existing one gained I9;
  two `RedisHoldWriterTest` tests with deliberate Redis drift name I10.

### D-020 Seat map API: static layout plus an availability bitset (DRAFT)
- **Date:** 2026-11-11
- **Context:** M1.8's seat map page needs every seat's position, label and tier, and which seats are
  free. PRD 10 names one endpoint, `GET /events/{id}/seatmap`, returning "bitset + sequence number"
  for M5's realtime diffs. Nothing produces a sequence number yet. SecurityConfig's public rule
  `/events/*` matches one path segment only, so a sub-path of an event needs its own rule.
- **Options considered:**
  - Shape: one payload (layout, seats and bitset); a static layout plus a separate status bitset;
    one payload with a status string per seat.
  - Access: both public; layout public and status behind login.
  - Bits: one per seat (available or not); two (available, held, sold).
  - Sequence number: a placeholder now; none until M5.1 produces one.
- **Decision:**
  - **Two endpoints, both public GETs** in internal `inventory.catalog`:
    `GET /events/{id}/layout` (venue size, stage, section outlines from `venues.layout_json`, and
    every seat with id, section, row, number, x, y, tierId, aisle, accessible) and
    `GET /events/{id}/seatmap` (`{eventId, seatCount, available, asOf}`).
  - **They are joined by position.** The layout lists seats `ORDER BY seat_id`, which is PostgreSQL's
    byte-wise uuid order (the same as comparing lowercase text, and **not** Java's signed
    `UUID.compareTo`). Bit i of the seat map describes `seats[i]`. Documented in the OpenAPI
    descriptions and docs/venue-format.md.
  - **One bit per seat**, 1 = AVAILABLE, most significant bit first, base64 with padding, unused bits
    zero. 2,014 seats are 252 bytes.
  - **No sequence number until M5.1** (a deliberate deviation from PRD 10). `asOf` is the snapshot
    time (`now()` of the one statement), which also corrects the client's clock. M5.1 adds `seq` as a
    new field, which doesn't break clients.
  - The seat map is **one statement** (existence check, seats and `asOf` from one snapshot). The
    layout is two statements (venue, then seats), because nothing in it changes after seeding.
  - Unknown or DRAFT event: 404 EVENT_NOT_FOUND; malformed id: 400; incomplete `layout_json`: 500
    (a data bug: seeded venues always have it).
  - **Security:** `GET /events/*/layout` and `GET /events/*/seatmap` are permitted one by one, not
    `/events/**`, so a future GET under an event stays behind login unless made public on purpose.
  - Frontend: `/holds`, `/orders`, `/me` and `/tickets` join the Vite dev proxy; app pages may not
    start with any proxied prefix (so the wallet is `/wallet`).
- **Why:**
  - The layout is about 2,000 seat objects and never changes; the status changes constantly. Split,
    the page downloads the layout once and refreshes 252 bytes after each rejected hold, and M5's
    WebSocket snapshot can reuse the bitset as it is (at 20,000 seats a combined payload would be
    re-sent in full on every refresh).
  - One bit is all a buyer needs (can I pick it?). Held versus sold matters to the operator heat
    view (M5.5), which can get its own encoding.
  - A placeholder sequence number would look meaningful to a client and mean nothing.
  - Public, like `/events`: people look before they log in. Reads take no locks (a plain SELECT reads
    a snapshot and never waits for the row locks holds take), so polling doesn't slow buyers down.
- **Trade-offs:**
  - Two requests on page load, and a positional contract between them: if the seat set of an event
    ever changed, a cached layout and a fresh bitset would disagree. `seatCount` lets the client
    detect that (the decoder throws on a length mismatch). Seats don't change after seeding today.
  - Anonymous clients can poll the seat map; nothing limits that until M4 (rate limits, admission).
  - No HTTP caching headers on the layout yet; TanStack Query keeps it for the page's lifetime.
  - Two generic-sounding schemas were prefixed (`LayoutRect`, `LayoutPoint`) because OpenAPI
    schema names share one namespace.
- **How I'd know it was wrong:** the layout's size or time shows up in the M2.4 load test or the PRD 8
  performance budgets (then gzip/ETag, or a compact array encoding); M4.2 finds bots scraping the
  seat map (then require the admission token for `/seatmap`); M5.1 can't express its diffs against
  this bit order; or the client's length check ever fires.

### D-021 Optimistic inventory strategy: version-checked writes, bounded retries, SEAT_CONTENDED (DRAFT)
- **Date:** 2026-11-13
- **Context:** M2.1 adds strategy B of PRD 6.2 behind `InventoryStrategy`: no `SELECT … FOR UPDATE`,
  each seat written with `UPDATE … WHERE version = <read>`. Three things were open: what to do when a
  write loses (retry how often, how long to wait), what the caller gets when retries run out (D-015
  anticipated a third rejection, `CONTENDED`), and how to count conflicts for the M2.5 benchmark.
  Optimistic UPDATEs still lock rows, so the write order matters, and D-015's "callers must not be
  `@Transactional`" matters more: a retry needs each try to be its own transaction.
- **Options considered:**
  - Retries: 3 tries with exponential backoff and full jitter; 2 tries without backoff; 5 tries with a
    fixed delay; a time budget instead of a count. Retrying a seat that is HELD or SOLD: never; yes.
  - Out of retries: a new `CONTENDED` rejection and 409 `SEAT_CONTENDED` with `Retry-After`; the same
    rejection mapped to 409 `SEAT_TAKEN`; 503 with `Retry-After`; `SEAT_TAKEN` from the strategy itself.
  - Counting: Micrometer counters and a timer; an `attempts` field on the outcomes; DEBUG logs; a table.
  - Release and sell: shared with the pessimistic strategy (extracted into `HoldClosing`); delegate to
    the pessimistic bean; separate optimistic versions.
- **Decision:**
  - **One try** (`OptimisticInventoryStrategy`): an unlocked read of the seats `ORDER BY seat_id`
    (with each owner's `created_at` and `clock_timestamp()` in the same statement, for `takenAgoMs`);
    UNKNOWN_SEAT; `EventSeat.hold` decides every seat (HELD or SOLD: SEAT_TAKEN, no retry); insert the
    hold row (the foreign key needs it first; a new row nobody can wait for); one UPDATE per seat with
    `AND version = :read` in the read's order; then the D-016 allowance upsert (LIMIT_EXCEEDED marks
    the try rollback-only). Zero rows on any UPDATE throws an internal `VersionConflict`, which rolls
    back the hold row and every seat written in that try.
  - **Write order = lock order.** An UPDATE locks its row until commit, so the loop over the read's
    rows (Postgres `seat_id` order, never a Java sort) is the lock order: the same as the pessimistic
    strategy, release, sell and the sweeper (D-015). Not one batched UPDATE, whose locking order would
    be the scan order. A deadlock (40P01) is not retried; it stays an exception for I7.
  - **Transactions:** `hold()` is `@Transactional(propagation = NEVER)` (a caller's transaction is an
    error) and runs each try through a `TransactionTemplate`. The backoff sleep happens between tries
    with no transaction or connection held.
  - **Retry policy:** at most 3 tries; before try n a random sleep in `[0, min(50 ms, 5 ms × 2^(n-2))]`
    (full jitter); `stampede.inventory.optimistic.max-attempts/backoff-base/backoff-max`. Only a lost
    version check is retried; a seat that reads HELD or SOLD is a real rejection.
  - **Out of retries:** `HoldRejection.CONTENDED` with the seat the last try lost on, mapped to
    **409 `SEAT_CONTENDED`** with `seatIds` and `Retry-After: 1` (the header comes from the error
    code, so the spec documents it on every operation that can return it). Precedence UNKNOWN_SEAT >
    SEAT_TAKEN > CONTENDED > LIMIT_EXCEEDED. The seats page explains it, keeps the selection and
    offers "Try again".
  - **Counting:** `stampede.inventory.hold.attempts{strategy}`, `…conflicts{strategy}` and the timer
    `…duration{strategy,outcome}` (outcome: held, seat_taken, contended, limit_exceeded, unknown_seat,
    error). Tags are only strategy and outcome, never an id, so the number of series stays fixed. The
    pessimistic strategy records the same meters (one attempt per call, no conflicts). Exposing them
    (`/actuator/metrics` or a Prometheus registry) is left to M2.5.
  - **Release and sell** are shared: both start by locking the hold row, and only a path holding it
    can change that hold's seats, so an optimistic version would remove no waiting. Extracted
    unchanged into `HoldClosing`; the shared seat SQL into `SeatRows`.
  - No event uses the strategy yet; switching per event is M2.3.
- **Why:**
  - A conflict on a seat almost always means it is now HELD, so try 2 mostly turns a race into an
    accurate SEAT_TAKEN with the right seats and `takenAgoMs`. Try 3 covers seats that churn (held and
    released in between). Jitter keeps losers of the same race from colliding again in step.
  - SEAT_TAKEN for a lost race would tell a buyer a seat is taken when it may still be free, and the
    benchmark couldn't tell lost races from taken seats. A 503 would count normal contention as a
    server failure.
  - Counters with bounded tags need no new dependency (Micrometer comes with Actuator) and read the
    same way for all three strategies.
- **How I'd know it was wrong:** the M2.4/M2.5 runs show many CONTENDED answers on seats that end up
  unsold (more tries or a longer backoff needed), or long tails from backoff (fewer tries); the harness
  or k6 logs a 40P01 for this strategy; conflicts per hold stay high where pessimistic lock waits are
  short (optimistic is the wrong default for hot seats, which is the M2.6 analysis); or Retry-After: 1
  makes clients retry in step (then jitter it on the client too).

### D-022 Redis-first strategy: keys, Lua scripts, stream persistence, and who wins (DRAFT)
- **Date:** 2026-11-13
- **Context:** M2.2 adds strategy C of PRD 6.2: a Lua script takes seats in Redis and Postgres is
  updated afterwards. Open questions: how keys are named and kept apart between test contexts that
  share one Redis; how the per-user cap (D-005) survives holds that expire by TTL with no code
  running; how holds reach Postgres, whose `event_seats.hold_id` and `orders.hold_id` have foreign
  keys to `holds`; which store wins when they disagree; and how much disagreement invariant 5 (PRD
  6.10) tolerates (PLAN change 6). Split into M2.2a (Redis alone), M2.2b (persistence, reconciler)
  and M2.2c (strategy bean, sell, invariants, harness), M2.2c itself split into M2.2c-1 (strategy,
  sell, catch-up, contract split) and M2.2c-2 (invariant 5, stuck-sweeper rule, harness).
  **Implemented: M2.2a, M2.2b, M2.2c-1, M2.2c-2 (all of M2.2); M2.2d (non-blocking I10 read).**
- **Options considered:**
  - Persistence: a Redis Stream with a consumer; synchronous write-through in the request; an
    in-process queue.
  - Disagreement: Postgres wins and Redis-only live holds roll forward; Postgres wins strictly
    (delete what it doesn't have); Redis wins for live holds.
  - Invariant 5 window: 2 s; 5 s (the sweeper interval); 30 s (the monitor's grace).
  - Cap in Redis: an integer counter per (event, user); a recount from the user's live holds.
  - Test isolation: a key prefix per Spring test context; a Redis database number per context.
  - Expiry: one TTL per key; explicit deletion by a sweeper.
- **Decision:**
  - **Keys** (prefix `p` = `stampede.inventory.redis.key-prefix`, default `stampede`; `RedisKeys` is
    the only place the formats are written in Java):

    | Key | Type | Content | Expires |
    |---|---|---|---|
    | `p:ev:<event>:meta` | hash | `limit`, `seatCount`; its existence means "event loaded" | never |
    | `p:ev:<event>:seats` | set | every seat id of the event | never |
    | `p:ev:<event>:seat:<seat>` | string | `H:<holdId>:<createdMs>` while held; `S:<orderId>:<soldMs>` once sold (M2.2c) | with the hold; never when sold |
    | `p:ev:<event>:hold:<hold>` | hash | `user`, `seats`, `n`, `createdMs`, `expiresMs` | with its seats |
    | `p:ev:<event>:user:<user>` | sorted set | member `<holdId>:<seat count>`, score = expiry in ms | with its last member |
    | `p:ev:<event>:closed` | string | the gate (M2.3a, D-023): while it exists `hold.lua` answers CLOSED and `load.lua` writes nothing | never; deleted when the event switches to REDIS_FIRST |
    | `p:inv:stream` | stream | HELD / RELEASED entries (no SOLD entry: see M2.2c-1) | trimmed after ack (M2.2b) |

  - **`hold.lua` checks everything before it writes anything**, in this order: event loaded
    (`NOT_LOADED`), every seat in the seat set (`UNKNOWN_SEAT`), no seat key exists (`SEAT_TAKEN`
    with `takenAgoMs` from the newest key's time), the cap (`LIMIT_EXCEEDED`), the hold id not live.
    Then it writes every seat key, the hold hash and the user member with the **same absolute expiry
    millisecond** (Redis `TIME` + the hold duration, D-015's "own authoritative clock") and appends a
    HELD entry to the stream. Precedence is D-016's; CONTENDED never occurs.
  - **`release.lua`:** no hold hash is `GONE`; an EXPIRED release of a hold that still exists is
    `NOT_EXPIRED` (expiry needs no script, the TTL does it); otherwise it deletes each seat key only
    if it still names this hold, removes the user member, deletes the hash and appends RELEASED.
  - **The cap is recounted, not counted** (a deliberate change to D-005's "the same counter as a
    Redis key"): the script adds up the seat counts of the user's members whose score is still in
    the future. A hold that expires stops counting at the millisecond its seat keys disappear, with
    nothing to decrement.
  - **Persistence: Redis Stream + consumer** (M2.2b). The entry is appended by the same script as
    the hold, so no hold exists without its entry. The consumer applies entries to Postgres through
    `EventSeat` (the state machine still guards every Postgres seat change), idempotently.
  - **On disagreement Postgres wins; a live hold only Redis knows is lag, not disagreement, and is
    persisted** (rolled forward). A conflicting fact in Postgres (seat SOLD, seat held by another
    unexpired hold, hold closed) wins and Redis is repaired. A sale always needs the Postgres hold
    row and `uq_order_items_active_seat`, so "Redis is never trusted alone" still holds for sales.
  - **Invariant 5: 2 s at runtime, zero in tests after the stream is drained, and it compares by
    time, not by status.** A Postgres hold whose `expires_at` has passed counts as expired, so the
    gap between a Redis TTL running out and the sweeper's 5 s tick is never reported as a mismatch;
    the 2 s window only measures consumer lag.
  - **Isolation: a key prefix per Spring test context** (`TestDatabases.registerRedis` for slices,
    `app_keys_N` from `TestcontainersConfiguration` for application contexts). Tests delete their
    own prefix with SCAN (`TestRedis.deleteKeys`), never FLUSHDB.
  - **Seat map** keeps reading Postgres (D-020): a new hold can show as free for the consumer lag,
    an expired one as taken for up to one sweeper tick. Redis still decides every hold attempt.
  - **Durability:** AOF with `appendfsync everysec` and `maxmemory-policy noeviction` (made explicit
    in compose in M2.2b). A crash can lose about the last second of acknowledged holds.
  - M2.2a's `RedisHoldStore` is not itself an `InventoryStrategy`; `RedisFirstInventoryStrategy` (M2.2c-1)
    is, and uses it.
  - **M2.2b, persistence and reconciler** (decided 2026-11-13: every instance runs a consumer;
    dead-letter after 5 non-transient failures; reconciler every 30 s; a cap disagreement is a
    Postgres-wins conflict):
    - **Loader** (`RedisEventLoader`, `redis/load.lua`): one read-only REPEATABLE READ snapshot of
      seats, limit, SOLD seats (`S:<orderId>:<order created ms>`), bought seats per order as a `+inf`
      cap member, and ACTIVE holds; then one script writes all of it or nothing, `meta` last with a
      `loadedMs` load epoch. If `meta` exists the script writes **nothing**: restoring a hold into a
      loaded event could resurrect one released in Redis whose RELEASED entry isn't applied yet.
      Holds already expired by Redis `TIME` are skipped. Runs on the reconciler's first pass at
      startup, on every pass for an event without `meta` (rule R0), and (M2.2c) on `NOT_LOADED`.
      Never under a row lock (review L2, 2026-11-15): a release or sale whose gate finds the event
      missing rolls back and loads it outside the transaction (see the review follow-up below).
    - **Consumer** (`RedisStreamConsumer`, thread in `RedisConsumerLifecycle`): group
      `inventory-persister`, consumer name = `stampede.inventory.redis.consumer.name` or the host name
      (unique per instance). On start it re-reads its own pending list from `0`; then `XREADGROUP
      COUNT 100 BLOCK 1s` (below the 2 s Lettuce timeout; one connection bound to the thread). `XACK`
      only after the Postgres commit. Every 10 s: `XPENDING` + `XCLAIM` of entries idle ≥ 30 s (also
      its own failed ones), and `XTRIM MINID =` the oldest pending id or the group's last-delivered
      id. `NOGROUP` (Redis lost the stream) recreates the group. Transient failures (unreachable,
      timeouts) stop the batch, back off 1 s doubling to 5 s and never count; any other failure stays
      pending, and at 5 deliveries the entry is copied to `p:inv:dead` (`MAXLEN ~ 10000`) with the
      error and acknowledged. The reconciler repairs what it would have written.
    - **Applying** (`RedisHoldWriter`, idempotent; the `holds` row is the gate): HELD inserts the
      row first with `ON CONFLICT DO NOTHING` (untargeted since M2.2c-2: the primary key and
      `uq_holds_id_event`; an existing row in any status = already handled),
      then the seats `ORDER BY seat_id FOR UPDATE`, the state machine, the allowance upsert (D-015
      order). It inserts ACTIVE only if Redis still has the hold; otherwise a tombstone row (EXPIRED if
      its time has run out by Redis' clock, else RELEASED). RELEASED closes an ACTIVE row through
      `HoldClosing.closeAsRedisDecided` (no Postgres-clock re-check; Redis' clock decides), or, if
      Postgres has no row yet, inserts the tombstone, so a HELD redelivered later is a no-op
      (`release.lua`'s entry now carries `createdMs`/`expiresMs` for that row). Concurrent HELD and
      RELEASED of one hold meet on the primary key. A HELD blocked by a seat held in Postgres, or by
      the cap, first closes the blocking holds Redis no longer has (each in its own transaction:
      their row lock would come after seat locks) and retries; still blocked (seat SOLD, a
      holder Redis still has, a seat Postgres doesn't have, the cap) = **Postgres wins**: tombstone
      RELEASED, `S:` markers back for sold seats, then `release.lua` in Redis. (Since the review
      follow-up, items M3 and M5 below: after each close pass the hold itself is re-checked, and more
      passes run while a pass finds a blocking hold gone from Redis.)
    - **Expiry:** `RedisHoldWriter.expire` for the M2.2c strategy's `release(…, EXPIRED)`, so the
      sweeper doesn't change: `NOT_EXPIRED` from Redis = NotExpired; `GONE` = close by Redis' clock,
      except while the event isn't loaded (then NotExpired: the loader decides). Lock-first since
      M2.2c-1 (below).
    - **Reconciler** (`RedisReconciler`, every 30 s on every instance, fixed delay): R0 load; R1 roll
      forward a Redis hold with no row, older than 5 s (`min-age`); R2 close a Postgres ACTIVE hold
      Redis doesn't have (re-reading Redis per hold, and stopping the pass if the load epoch
      changed); R3 force SOLD markers and `+inf` members (releasing in Redis a hold the key named, or,
      if that hold is CONVERTED, finishing its sale with `sold.lua` instead: review M1);
      R4 release in Redis a hold whose Postgres row isn't ACTIVE. It uses the consumer's writer
      methods, so whichever comes second is a no-op.
    - **Metrics:** gauges `stampede.inventory.redis.stream.lag` (pending + undelivered) and
      `…stream.oldest.age` (ms, Redis clock; what invariant 5 and M2.5 read), counters
      `…redis.applied{type,result}`, `…redis.deadletters`, `…redis.reconciler.repairs{rule}`.
    - **Compose:** `--appendfsync everysec --maxmemory-policy noeviction` (no `maxmemory` set yet).
  - **M2.2c-1, the strategy and sell** (decided 2026-11-14: sell = pin, Postgres sale, `sold.lua`;
    catch-up = this hold only, through `applyHeld`, also on cancel; the retry rule reads Redis):
    - **`RedisFirstInventoryStrategy`.** `hold` touches only Redis: `RedisHoldStore.tryHold`, and on
      `NOT_LOADED` it loads the event and runs the script once more (`HoldMetrics.attempts` counts
      both runs; `conflicts` is always 0). `release` and `sell` work like the Postgres strategies:
      **lock the `holds` row first**, run the Lua script while holding that lock, then write Postgres in
      the same transaction (`HoldClosing.closeWith` / `sellWith`: a gate called once the row is locked
      and ACTIVE; the Postgres strategies pass today's database-clock check through the same gate,
      unchanged). So a sale, a cancel and the sweeper for one hold take turns on that row lock, and
      the checkout's compensating release stays definitive (D-017). Release writes Postgres
      synchronously; its RELEASED entry is a no-op (DUPLICATE) for the consumer later.
    - **Release, RELEASED or SAGA_FAILED:** catch-up, lock, `release.lua`. RELEASED = close.
      GONE = Redis already ended the hold (TTL, or a release whose Postgres write failed): Postgres
      records it, EXPIRED or RELEASED by Redis' clock, and the caller gets `NotActive(that status)`
      (a cancel is 204, a failed checkout cancels and refunds). GONE while the load epoch changed
      means nothing yet: load, run the script once more.
    - **Release, EXPIRED** (the sweeper): `RedisHoldWriter.expire`, now lock-first too, with the same
      epoch check. `release.lua` change: an EXPIRED release of a hash whose `expiresMs` has passed
      releases it. Only a pinned hold can be in that state (no TTL); EXPIRED releases write no stream
      entry (the sweeper closes Postgres itself, and retries on its next tick if that fails).
    - **Sell, three steps, so a sale never exists in Redis without Postgres:**
      1. `pin.lua`, under the row lock: PERSIST the hold hash and its seat keys, member `+inf`, user
         key PERSIST. No hash = `HoldExpired`; a hash past its expiry (an earlier pin that never
         finished) = `HoldExpired`. Nothing is written in either case; the sweeper closes the hold.
      2. The Postgres sale in the same transaction (seats `ORDER BY seat_id`, `EventSeat.sell`,
         CONVERTED), with no database-clock expiry check: Redis' clock decided in step 1.
      3. After the commit, `sold.lua`, one script: `S:<orderId>:<ms>` markers with no expiry, member
         `+inf`, hold hash deleted. A seat key naming another hold is overwritten (Postgres sold it) and
         that hold is released in Redis, as R3 does. One retry, then a WARN; the sale stands.

      | Fails at | Redis | Postgres | Repaired by | Caller |
      |---|---|---|---|---|
      | step 1 (hold gone) | unchanged | unchanged | sweeper (the consumer or R2 if GONE came from a release whose Postgres write failed) | 410, refund |
      | step 2 | pinned, seats still `H:` | rolled back, ACTIVE | compensating release (`release.lua` finds the hash) | 500, refund |
      | crash after step 1 | pinned | ACTIVE, expires | sweeper: `release.lua` EXPIRED once past `expiresMs` | PENDING order (D-017 crash limit) |
      | step 3 | pinned: seats taken, cap counted | SOLD, CONVERTED | strategy retry; then R4 | 201 |
      | answer lost after step 2 | pinned | CONVERTED | compensation sees CONVERTED, finishes the order; R4 | 201 |

    - **No SOLD stream entry:** the sale is written to Postgres synchronously, so an entry would only
      ever be a no-op. (The key table said "SOLD in M2.2c".)
    - **Reconciler R4 change:** a Redis hold whose row is CONVERTED gets `sold.lua`, not `release.lua`.
      Releasing it would free sold seats in Redis (the M2.2b note). Counted with the sold markers,
      metric `R4_finish_sale`.
    - **Catch-up** (`RedisCatchUp`, public, used by `HoldService`): for one hold, if Postgres has no
      row and Redis has the hold, `RedisHoldWriter.applyHeld` (R1's roll-forward). Called by
      checkout step 0 (`HoldService.checkoutHold`, only when the row isn't found, so the Postgres
      strategies pay nothing), by `HoldService.cancel` (same), and by the strategy's release and sell
      (after `ensureLoaded`). POST /orders and DELETE /holds/{id} carry only a hold id, so it looks
      in each open REDIS_FIRST event (one HGETALL each). Cost: one or two Redis reads, independent
      of the backlog. `booking.checkout` is unchanged.
    - **The retry rule (D-016) for REDIS_FIRST reads Redis:** on SEAT_TAKEN, the caller's own live
      Redis hold whose seat set equals the request (found through the first seat's key) is persisted
      by catch-up and returned with 200. Postgres can't answer: during consumer lag it doesn't have
      the hold, and it can still show a hold Redis has already expired.
    - **Epoch guards:** the consumer's "close older holds Redis no longer has" step reads the load
      epoch before its Redis checks and stops before a close if it changed, like R2. Both guards are
      tested by wiping and reloading Redis at the exact moment they protect (a package-private test
      hook in `RedisHoldWriter` and `RedisReconciler`); both tests fail with the guard removed.
    - **Contract tests:** `InventoryStrategyContractTest` is now the behaviour contract all three
      strategies run (10 tests; Redis through a test decorator that drains the stream after each
      call). `PostgresLockingContractTest` holds the 34 tests that set state up with SQL or probe
      Postgres locks (moved unchanged, checked byte for byte). `RedisFirstInventoryStrategyTest`
      covers those behaviours through Redis-first's real paths, plus a 100-round sell-versus-release race.
  - **M2.2c-2, invariant 5, the stuck-sweeper rule and the harness** (decided 2026-11-14: stuck = 2 min,
    the same at runtime and in tests (C1); rule id I10; a sale between its Postgres commit and `sold.lua`
    is excused at runtime like O1/O5 (option B)):
    - **Reader:** `inventory.api.RedisHoldState` (read-only), implemented by `inventory.strategy.RedisHoldStateReader`
      with one script, `redis/state.lua`: Redis `TIME`, limit, seat set, every seat key (`MGET` in
      chunks), every hold hash with its PTTL (-1 = pinned), every user set, and this event's stream
      entries the group hasn't acknowledged (pending, plus after `last-delivered-id`) younger than the
      window. Whole event (`SCAN MATCH <p>:ev:<event>:*` inside the script) or only listed keys (a
      re-read, plus the holds their values name). Keys come from `RedisKeys`: own prefix only.
    - **Rule I10** (`control.invariants.RedisConsistencyCheck`), REDIS_FIRST events loaded in Redis only:
      1. Redis is read **before** the checker's Postgres snapshot exists (REPEATABLE READ takes it at the
         first query), so for holds Redis takes, Postgres can only be behind Redis. Postgres is *ahead*
         for a sale between its commit and `sold.lua`, for a Postgres-wins tombstone before `release.lua`,
         and for R3's markers; the re-read and the sale-finishing excuse cover those (review doc fix).
         Inside the snapshot: limit, `event_seats`,
         ACTIVE and CONVERTED holds (with their newest order's age).
      2. Both sides normalised **by Redis time**: a hold is live while its expiry is in the future (a
         pinned hash past its expiry is expired); a seat is held only by a live hold; cap = live members
         vs live ACTIVE + CONVERTED holds. Compared: limit, seat set, live holds (user, seats, created,
         expiry), every seat, every user's cap. An `H:` key naming a missing hash is reported.
      3. What disagrees is **re-read from Redis** (those keys only) after the snapshot and compared again
         at the new time: a release or an applied hold that landed between the read and the snapshot.

- **Why:**
  - Redis runs commands on one thread and a whole script as one command, so nothing can happen
    between a script's checks and its writes: that is the entire locking story of this strategy.
    Redis does not roll back a script that fails halfway, hence "all checks, then all writes".
  - One expiry instant for every key of a hold means a reader never sees half an expired hold.
  - A counter decremented on expiry would need code to run at expiry (keyspace notifications are not
    guaranteed, PRD 6.3), and one missed decrement locks a user out. A recount can't drift.
  - A stream written inside the script is a transactional outbox inside Redis: the hold answers
    after one round trip, and the Postgres write can fail and be retried without losing the hold.
  - Rolling forward keeps holds buyers were told they have when the consumer is slow; letting
    Postgres win conflicts keeps a checkout in progress safe when Redis loses data.
  - A prefix works on any Redis (there are only 16 numbered databases and 15 test contexts already).
- **Known limits:**
  - (M2.2b) A hold released in Redis whose RELEASED entry is still unapplied when the sweeper or R2
    reaches it after its expiry time is recorded EXPIRED, not RELEASED (status only; seats and
    allowance are the same). A hold id reused after its hold ended (D-015 bug) makes its HELD a
    no-op; logged at ERROR. The load script grows with the event (about 150 KB of arguments for
    2,000 seats) and blocks Redis while it runs. (The consumer pre-close step's missing epoch guard
    and the untested R2 guard were fixed in M2.2c-1.) Both epoch guards still have a window between
    the epoch comparison and the close's commit, as R2 always had. It is wider than milliseconds
    (review L3): after the comparison, `closeGone` reads the hold, checks `isLoaded` and then waits for
    the hold row lock, as long as a concurrent sale or release of that hold holds it (up to the 2 s Redis
    timeout per call), and it does not ask Redis again under the lock. A wipe and reload in that window,
    with that concurrent sale rolling back, closes a hold Redis has restored: the buyer loses it, and R4
    frees it in Redis on the next pass.
  - (M2.2c-1) **404 instead of 410:** if a REDIS_FIRST hold's TTL runs out (about 5 minutes) before
    the consumer or any catch-up has written its row, Postgres never has the hold and Redis no longer
    does, so catch-up finds nothing: POST /orders and DELETE /holds/{id} answer 404 HOLD_NOT_FOUND
    instead of 410 HOLD_EXPIRED / 204. It needs a consumer that is minutes behind. (A buyer's release
    can't cause it: the strategy's release persists the hold first.)
  - (M2.2c-1) Release and sell call Redis while holding a Postgres row lock: usually a few ms, but a
    gate can make up to about 5 Redis calls (epoch, script, epoch again, a second attempt). If Redis
    stalls, that hold's row stays locked for up to the Redis command timeout (2 s) per call; other
    holds are not affected. (It no longer includes a whole event load: review L2.)
  - (M2.2c-1) The retry rule finds the caller's hold through the first requested seat's key. That is
    exact (every seat of a hold names it), but a hold pinned by a sale in progress is also returned
    (200) while it is being converted, as the Postgres rule would.
  - Single Redis node assumed: the scripts build seat and user key names from a prefix instead of
    declaring every key, and there is one stream. Redis Cluster would need hash tags per event.
  - A hold id reused after its hold expired is not caught in Redis; the `holds` primary key catches
    it at persistence.
  - Redis' clock and Postgres' clock are two clocks; for REDIS_FIRST events Redis decides expiry and
    Postgres stores Redis' times.
  - After a crash inside the AOF window, a buyer can lose an acknowledged hold (410 at checkout). It
    is worse than that (review L4): `pin.lua`, `sold.lua` and `release.lua` writes are lost too, and
    `meta.loadedMs` survives, so no epoch guard notices. A lost pin plus `sold.lua` of a sale committed
    near its expiry frees its sold seats in Redis once the restored TTL runs out (other buyers are told
    "held", then lose to Postgres wins) until R3 or R4 run, up to 30 s; a lost `release.lua` of a
    committed cancel keeps its seats blocked and the cap over-counted in Redis until R4. Not tested
    automatically. A fix would run R3/R4 at once when a Redis restart is seen (its `run_id` changes).
  - (Review L5, second half) `removeGoneHoldMember` and `addSoldMember` are two Redis commands each,
    not one script: a crash between them leaves the member half-changed (a `+inf` member on a user key
    that still expires; R3 puts it back). Only after a crash; Postgres still enforces the cap.
  - (Review L6) `state.lua` reads at most the 10,000 oldest undelivered (and pending) stream entries
    across all events. With a larger backlog arriving within 2 s, young entries are missed, so lag under
    2 s is reported by I10. Depends on M2.5 rates; a fix reads the undelivered range from
    `max(last-delivered, now - window)`.
  - (Review L1, the cap half) I10 counts a `+inf` member of a pinned hold past its expiry as not live
    (it is over by time), while `hold.lua` keeps counting it until the sweeper releases it (up to one
    5 s tick). I10 can't see drift in that state for that time.
  - (M2.2c-2, **resolved in M2.2d**) `state.lua` blocked Redis for about 40 ms per check on a loaded
    2,000-seat event (one script over the whole event). The first read is now paged: its longest single
    command is ~1 ms (table in "M2.2d" above).
  - (M2.2d) **A torn first read can hide drift for one check.** The paged first read decides what is
    read again. Drift on keys nobody writes is always seen (SCAN returns every key that exists for the
    whole scan, and an unchanged key reads the same paged or not). But if a write to the same seat, hold
    or user lands between the reads of two keys in different pages and makes them look consistent with
    Postgres, that drift is not read again and not reported in that check; the next check (30 s later)
    sees it unless the coincidence repeats. Tests read a quiet Redis (after draining), so strict checks
    are unaffected.
  - (M2.2d) What a check still costs Redis: the re-read is one atomic script sized by the number of
    disagreeing keys (plus `SMEMBERS` of the seat set), so heavy churn makes it longer; the `HEAD` call's
    stream part (`XPENDING` + `XRANGE`, up to 10,000 entries, see L6) is long under a large backlog; the
    `SCAN` still walks the whole keyspace, now in short pages. A paged read takes ~0.5 s of round trips
    on Docker Desktop (no Postgres connection held).
  - (M2.2d) A reload is noticed by the load epoch (`meta.loadedMs`). An event loaded by
    `RedisHoldStore.loadEvent` (tests only) has no epoch, so a reload during the read is not noticed there.
  - (M2.2c-2) A lost live cap member (partial Redis data loss) is never put back: no reconciler rule
    does it. Postgres still wins at persistence, so the cap holds in Postgres; invariant 5 reports the
    undercount for as long as the hold lives (`RedisHoldWriterTest#whenRedisUndercountsTheCapPostgresWins`
    documents it with `@ExpectInvariantViolations({"I10"})`).
  - (M2.2c-2) I10 is checked only for events loaded in Redis: after a Redis restart, nothing is compared
    until the reconciler's R0 reloads the event (up to 30 s).
  - (M2.2c-2) Called inside an existing transaction (the after-test listener, the harness), I10 reads
    Redis after that transaction's snapshot, and its Postgres re-read (M2.2d) joins that transaction too.
    Fine where nothing runs concurrently; the monitor opens a fresh transaction per event, so its order is
    right.
- **How I'd know it was wrong:** the harness (M2.2c) or invariant 5 finds a seat with two live
  holders or a user over the cap; invariant 5 fires in normal load (the consumer can't keep up, or
  2 s is too tight); I9 fires at runtime (the sweeper is stuck or keeps failing on a hold); the M2.5

  the catch-up before checkout dominates); buyers report holds that vanished without a Redis crash;

### D-023 Strategy switch per event: only while nothing is live (DRAFT)
- **Date:** 2026-11-18
- **Context:** M2.3 makes an event's inventory strategy selectable by an admin (PRD OP2,
  `POST /admin/events/{id}/strategy`), for benchmarking. Release, sell and the expiry sweeper pick the
  strategy from the event's *current* `events.strategy`, not from whichever strategy created a hold, so
  after a switch the new strategy acts on every existing hold. That is safe only if, at the moment of the
  switch, nothing is live that the new strategy can't see: a REDIS_FIRST hold only Redis has, an
  unapplied stream entry, or a hold that a request in flight commits just after the switch (the strategy
  and the sale window are read unlocked before the strategy runs: D-016's known limit). Also, `load.lua`
  writes nothing into an event whose meta exists, so Redis keys left from an earlier REDIS_FIRST period
  would be kept as if they were current.
- **Options considered:**
  - When a switch is allowed: (A) only while the event takes no holds and nothing is live, otherwise
    409; (B) the same window, with live holds carried over (Postgres to Redis by the loader; Redis to
    Postgres by a drain that persists every Redis hold and closes what Redis no longer has); (C) any
    time, the switch itself pausing and draining for a few milliseconds.
  - Redis keys after switching away from REDIS_FIRST: (a) delete at once; (b) keep them, inert;
    (c) let them expire after a TTL.
- **Decision:** A and a (decided by the user, 2026-11-18). Switching is a non-production benchmarking
  feature done between runs on a reset event, and B's live drain-and-carry adds exactly the kind of
  Redis/Postgres race surface that M2.2 showed is costly.
  - **Allowed when** the event is not ENDED, takes no holds (before its drop, or DRAFT, PAUSED or
    SOLD_OUT: the same rule as `HoldService`), has no ACTIVE hold in Postgres and, when switching away
    from REDIS_FIRST, no hold hash in Redis and no unapplied stream entry of the event (pending or not yet
    delivered). Otherwise **409 `STRATEGY_SWITCH_REFUSED`** with `reason` (ON_SALE, EVENT_ENDED,
    LIVE_HOLDS, LIVE_REDIS_HOLDS, UNAPPLIED_STREAM_ENTRIES, SWITCH_IN_PROGRESS) and the unchanged
    `strategy`. The same strategy again is 200 with `changed: false` and no audit row.
  - **Protocol** (`inventory.strategy.StrategySwitcher`, behind `inventory.api.StrategySwitch`):
    1. A **per-event advisory lock** (`pg_try_advisory_xact_lock(hashtextextended(...))` on a key derived
       from the event id) on a connection of its own, held for the whole switch; busy = SWITCH_IN_PROGRESS.
    2. From REDIS_FIRST: set the **closed gate** `p:ev:<event>:closed`. `hold.lua` checks it first
       (CLOSED) and `load.lua` writes nothing while it exists. Redis runs one command at a time, so every
       hold either ran before the gate (its hash and entry exist, and step 4 sees them) or is refused.
    3. One transaction: the event row `FOR NO KEY UPDATE`, then **every seat of the event** `ORDER BY
       seat_id FOR UPDATE` (D-015's order).
    4. The checks above, under those locks. To REDIS_FIRST: delete the event's leftover keys (all but
       the gate). `UPDATE events`, then the audit row through the caller's `AuditWriter`, then commit.
    5. After the commit: from REDIS_FIRST, delete every key of the event except the gate; to REDIS_FIRST,
       remove the gate and load the event. A failure here is logged, not thrown (the switch stands), and
       repeating the request finishes it. A refusal or failure before the commit removes the gate again.
  - **In-transaction re-check** in every strategy (`StrategyGuard`): the outcome `StrategyChanged` for
    hold, release and sell, with nothing written:
    - Pessimistic hold: after its seat locks, `strategy = own AND on sale`. Optimistic hold: after its
      seat UPDATEs (which lock the rows), the same check, then a rollback. Release and sell (all three
      strategies): the strategy, once the hold row is locked and before anything is written (for
      Redis-first, before any Lua runs). Redis-first hold: the gate (CLOSED), or the loader refusing an
      event that isn't REDIS_FIRST in its snapshot.
    - `HoldService` re-reads the event and retries once on the current strategy. Twice in a row is
      SALE_NOT_OPEN for a hold (a switch needs the event off sale) and an IllegalStateException for an
      existing hold (a switch needs no ACTIVE hold). The sweeper skips the hold until its next tick.
  - **Consumer guard:** an entry whose event is no longer REDIS_FIRST is acknowledged with nothing
    written (WARN, `stampede.inventory.redis.applied{result=not_redis_first}`). After a switch there are
    none (step 4 refuses while entries are unapplied); the guard covers a hand-edited strategy.
  - **Audit:** control owns `audit_log` (D-007), inventory owns `events`. Inventory calls the caller's
    `AuditWriter` inside the switch's transaction, so the row (actor = the admin's user id, action
    `event.strategy_changed`, entity `event:<id>`, before/after `{"strategy": ...}`) commits or rolls back
    with the switch. Inventory never depends on control.
  - **Endpoint:** `control.admin.AdminEventController`, ADMIN only through SecurityConfig's existing
    `/admin/**` rule (401 / 403 before the controller runs). The request is `{"strategy": ...}` with an
    enum (`inventory.api.EventStrategy`, kept equal to `StrategyKind` by a test).
- **Why:**
  - Option A needs no hold to move between strategies, so nothing has to be carried, drained or
    reconciled during a switch. The price is that a switch needs the event off sale and every hold
    ended, which is how a benchmark run is set up anyway.
  - The seat locks make the switch and a hold in flight take turns. A Postgres hold holding a seat lock
    makes the switch wait and is then counted as live (409); one that comes later waits for the switch
    and fails its re-check. The re-check is one unlocked primary-key read inside the strategy's
    transaction, so D-015's lock order is unchanged. The switch adds "event row before seats", and no
    other path locks event rows.
  - **`FOR NO KEY UPDATE`, not `FOR UPDATE`:** inserting a hold row checks its foreign key with a
    `FOR KEY SHARE` lock on the event row, which `FOR UPDATE` blocks. A hold holding a seat lock and
    inserting its row would wait for the switch while the switch waits for its seat: a deadlock (tested
    in `StrategySwitcherTest`). `NO KEY UPDATE` is what an UPDATE of a non-key column takes anyway, and
    it doesn't conflict with `KEY SHARE`.
  - The gate is kept after switching away (the only key not deleted), because a loader whose Postgres
    snapshot was taken just before the switch would otherwise load the event back into Redis afterwards.
    This is a small departure from decision 2a ("delete the keys at once"), accepted by the user on
    2026-11-18: one inert key per event that has left REDIS_FIRST, deleted when it switches back.
  - The advisory lock lives on its own connection inside a transaction, so it ends with that transaction
    (or the connection) and can't outlive the switch on a pooled connection.
- **Possible future upgrade: option B** (live holds carried over). The same locks, gate and re-check
  apply. It adds, when switching away from REDIS_FIRST, a drain under the gate (R1's roll-forward without
  the minimum age for every Redis hold, R2's close for every Postgres ACTIVE hold Redis no longer has)
  and, when switching to it, an eager load that restores the ACTIVE holds. The hold rows would need
  locking too (between a release's or sale's hold-row lock and its seat locks). Only worth it if
  benchmarks ever need to switch during a sale.
- **Known limits:**
  - **D-016's pause race is narrowed, not closed, for a pause on its own.** The re-check reads the
    window after the strategy's first seat lock, but a pause that commits between that read and the
    hold's commit still lets the hold through. The switch is airtight because it also takes every seat
    lock and counts holds under them. The M5.5 pause endpoint must do the same (lock the event's seats,
    and for REDIS_FIRST close a gate) to close the race. Redis-first holds have no sale-window check in
    Redis at all; only the gate stops them.
  - Each Postgres-strategy hold, release and sell pays one more primary-key read (the re-check), and
    each consumer entry one (the guard). Measured in M2.5 like everything else.
  - A switch locks every seat of the event for one transaction (milliseconds on 2,000 seats). It is
    only allowed off sale, so no buyer waits on it.
  - If the process dies between the commit and step 5, the event's Redis state is incomplete until the
    request is repeated. To REDIS_FIRST, the gate stays closed and every hold gets StrategyChanged, then
    SALE_NOT_OPEN; the same request removes the gate.
- **How I'd know it was wrong:** a benchmark needs to switch during a sale (then B); the re-check shows
  up in the M2.5 latency numbers; `not_redis_first` is ever counted at runtime; an invariant (I10 in
  particular) fires right after a switch; or 40P01 deadlocks appear in a run that switches strategies.

### D-024 Load tests: k6 in Docker, a fresh event per run, an on-demand strict verdict (DRAFT)
- **Date:** 2026-11-19
- **Context:** M2.4 adds k6 load scenarios (PRD 12) and `scripts/k6.sh`. Open questions: which k6, how test
  users get tokens without bcrypt (cost 12) dominating the numbers (M0.5 note), how each run starts from
  a known state and gets the strategy under test (the M2.3a switch needs the event off sale and no live
  hold), how a run is judged correct, and what is gated. Split into M2.4a (k6.sh, events, users, the
  verdict endpoint, smoke, seat-collision) and M2.4b (mixed-realistic, the repeat procedure, docs).
- **Options considered** (decided by the user, 2026-11-19; the letters are the plan's):
  - D1 k6 image: `grafana/k6:2.3.0` (current major) or `1.8.2` (the 1.x maintenance line).
  - D2 users: setup() registers and logs in each run; users inserted by SQL; k6 signs its own JWTs; a
    test-only endpoint that mints tokens.
  - D3 state between runs: a fresh warm-up and benchmark event per run (by SQL from the demo event),
    switched through the M2.3a endpoint; the same without the endpoint; reset the demo event in place;
    `docker compose down -v` per run.
  - D4 verdict: grep the monitor's log; `GET /admin/invariants`; SQL rules in the script.
  - D5 thresholds: correctness only (latency reported); latency gated too.
  - D6 pool exhaustion: measure (pg_stat_activity); expose Hikari metrics; add `lock_timeout` now.
  - D7 PowerShell: run k6.sh through Git Bash; a k6.ps1 twin.
- **Decision:** D1 `1.8.2`, D2 setup() logins, D3 fresh events + the switch endpoint, D4 the endpoint,
  D5 correctness only, D6 measure only, D7 Git Bash.
  - **k6** `grafana/k6:1.8.2@sha256:00fdcebafbc86cb0137d429529b1caa401a02e09025f02fc74866fa6e2b004d8`
    (pushed 2026-10-24), run on the compose network against `http://backend:8080`: no Docker Desktop
    port forwarding between k6 and the backend. `--target host` uses `host.docker.internal:8080` (bootRun).
  - **Events:** `scripts/k6/sql/bench-events.sql` inserts a warm-up event (on sale, the strategy under
    test) and a benchmark event (PESSIMISTIC, drop `--lead` seconds away, default 180), copying the demo
    event's venue, tiers and seats; only inserts, every seat AVAILABLE. setup() switches the benchmark
    event through `POST /admin/events/{id}/strategy` (it has never had a hold, so the switch is always
    allowed; to REDIS_FIRST it is also loaded into Redis). After the run (and before the next) every
    `k6 ...` event is set ENDED by SQL, so the invariant monitor stops checking it; events have no
    lifecycle code yet, so this is a plain status write, limited to titles starting with "k6 ".
  - **Admin:** `k6-admin@load.test`, registered through the API, given the ADMIN role in SQL (as the API
    tests do; the API can't make an admin). Its password is random, generated once by k6.sh into
    `benchmarks/runs/.k6-admin-password` (gitignored). k6.sh never reads `.env`: SQL runs inside the
    postgres container with that container's credentials.
  - **Users:** `k6-user-NNNNN@load.test`, one non-secret password; setup() registers (EMAIL_TAKEN is fine)
    and logs in all of them in parallel batches of 20, before the warm-up. One buyer per user, because
    the per-user cap counts sold seats for good.
  - **Verdict** (`GET /admin/invariants?eventId=&grace=`, ADMIN; `control.invariants.OnDemandInvariantCheck`):
    for a REDIS_FIRST event it first asks whether the stream still has unapplied entries of the event
    (`inventory.api.RedisStreamBacklog`, implemented by `RedisStreamConsumer`, the same exact check the
    switch uses), then runs the checker, and returns both. teardown() asks for each of the run's events
    until `unappliedStreamEntries` is false (at most 120 s), then counts that answer's violations.
    **Grace PT0S (strict)**, as in the test suite: k6 has had every response before teardown, checkout is
    synchronous (payment and tickets inside `POST /orders`), so no order is legitimately half done, and
    with the stream drained Redis and Postgres must agree exactly. Without `grace` the endpoint uses the
    monitor's grace (PT30S), so an operator looking during a live sale doesn't see in-flight checkouts.
  - **Gates** (k6 thresholds): no unexpected answer (5xx, timeouts, codes a scenario can't legitimately
    get), seats held and sold at most the hot block, zero violations, a conclusive verdict; k6.sh adds
    "the database has exactly the SOLD seats k6 counted". Latency, throughput and conflict rate are
    reported, not gated.
  - **Measured alongside:** `pg_stat_activity` once a second (the app's connections: active, waiting on a
    lock), `docker stats` about every 2 s (k6's own CPU included). Everything lands in
    `benchmarks/runs/<UTC time>-<scenario>-<strategy>/` with a `run.json` (commit, images, Docker CPUs and
    memory, parameters, verdict).
- **Why:**
  - Fresh events make every run start from the same state without rewriting state that only the
    strategies and the saga should write, and the old events stay for post-mortems.
  - Logging in through the API keeps the real token path; its cost is paid before anything is measured.
  - The verdict is the same checker, strict, that every test runs, so a load run is judged by the same
    rules; asking for the stream lag first is what lets I10 be strict for REDIS_FIRST.
  - Latency on one laptop varies with the machine; gating on it would make runs red for reasons that
    aren't the code's. M2.5/M2.6 judge the numbers across repeated runs.
- **Consequences:** the API gains an admin endpoint (openapi.json, frontend client). Every run leaves two
  ENDED events and ~4,000 event seats behind; `docker compose down -v` clears them (ask first). While a
  run is going, its two events are listed by `GET /events` (the board shows upcoming events that are
  neither DRAFT nor ENDED); once ended they disappear from it.
- **How I'd know it was wrong:** the verdict is inconclusive (stream lag never reaches zero) or reports
  violations that turn out to be timing, not bugs; setup's logins push the drop past the lead often;
  k6's own CPU is saturated in docker_stats.csv (then the numbers measure k6); runs on the same commit
  differ by more than the strategies do.
