# Design decisions

Write these yourself, in your own words. Each one is an interview answer you've already rehearsed.

## Template
### D-000 Title
- **Date:**
- **Context:** what problem forced a choice
- **Options considered:** at least two
- **Decision:**
- **Why:** the trade-off in one or two sentences
- **How I'd know it was wrong:** a measurement or symptom

---

### D-001 Modular monolith instead of microservices
- **Date:** 2026-11-07
- **Context:** I'm one person with about twelve weeks. The hard part of this project is contention:
  many buyers racing for the same seats. Splitting the system into services is a different problem.
- **Options considered:** microservices; a plain monolith with no internal boundaries; a modular
  monolith with enforced boundaries.
- **Decision:** One Spring Boot app split into eight modules (identity, inventory, booking, payments,
  ticketing, waitingroom, realtime, control). Modules talk only through each other's public API package
  or through events, and a Spring Modulith test fails the build if a module reaches into another.
  I run it as three identical instances behind Nginx.
- **Why:** Microservices would cost me network calls, distributed transactions and deployment work
  without teaching me anything more about contention. A plain monolith turns into a tangle. With
  enforced modules, I get clean boundaries now and could still split a module out later.
- **How I'd know it was wrong:** One module needs to scale differently from the rest. For example,
  waitingroom or realtime saturates the CPU while booking sits idle, so I'm forced to scale everything
  to scale one thing. Or the Modulith test keeps pushing me into workarounds that make the code worse.

### D-002 UUID v4 ids, generated by the app
- **Date:** 2026-11-08
- **Context:** Every table needs a primary key type, and I wanted one type everywhere.
- **Options considered:** bigint identity; UUID v4; UUID v7 (time-ordered); a hybrid with bigint for
  internal tables and UUIDs for public ones.
- **Decision:** UUID v4 everywhere. The app creates ids with `UUID.randomUUID()`, and
  `gen_random_uuid()` is the column default for rows inserted straight from SQL.
- **Why:** In the Redis-first strategy, the Lua script creates a hold before Postgres knows about it,
  so the id must exist before the insert. UUIDs also can't be guessed in URLs, so `/orders/1042`
  doesn't leak my sales volume. The cost is 16 bytes per id, and random values spread inserts across
  the index instead of appending at the end.
- **How I'd know it was wrong:** The benchmarks show index bloat or slow inserts on the busy tables
  (holds, order_items, outbox). Then I'd switch to UUID v7, which needs no migration because the
  column type stays `uuid`.

### D-003 Seat states narrowed to AVAILABLE / HELD / SOLD
- **Date:** 2026-11-08
- **Context:** The PRD's seat diagram also has CHECKED_IN and TRANSFERRED. But a checked-in or
  transferred seat is still sold. Those two states describe the ticket, not the seat.
- **Options considered:** keep all five states on `event_seats`, as the PRD draws it; keep only
  AVAILABLE/HELD/SOLD on the seat and move the rest to tickets.
- **Decision:** `event_seats.status` is AVAILABLE, HELD or SOLD. Tickets have ISSUED, CHECKED_IN or
  REVOKED. A transfer keeps the same ticket row and bumps its version and holder.
- **Why:** With five seat states, every "is this seat sold?" query and every invariant (for example,
  "every sold seat has a paid order") has to remember that three values mean sold. Keeping the seat to
  the three states that matter for contention keeps the hot path and the checks simple.
- **How I'd know it was wrong:** Seat-map or gate views keep joining tickets just to show a seat's
  state, or I find a rule that genuinely depends on the seat, not the ticket, being checked in.

### D-004 Seat transition guard in code, not a database trigger
- **Date:** 2026-11-08
- **Context:** The PRD says transitions are guarded "in code and in the database". A CHECK constraint
  can only limit which values are allowed. Stopping an invalid move such as SOLD to HELD in the
  database would need a `BEFORE UPDATE` trigger on `event_seats`.
- **Options considered:** a trigger that rejects transitions not in the diagram; a state machine
  class in code (M1.1) only, plus database constraints on the data itself.
- **Decision:** The guard lives in code. The database still enforces what it can check on a single
  row: the CHECK that ties status to `hold_id`/`order_id` (HELD needs a hold, SOLD needs an order), and
  the unique partial index on active order items.
- **Why:** `event_seats` is the hottest write path in the system. A trigger would run on every hold
  under contention and skew the benchmark that compares strategies. The trade-off is that code
  bypassing the state machine could make a bad transition without the database objecting. The index
  and the invariant checker after every test are my safety net.
- **How I'd know it was wrong:** The invariant checker catches a bad transition that came from code
  skipping the guard. Or I measure the trigger and its cost is negligible, in which case I'd add it.

### D-005 Per-user ticket cap via a counter row
- **Date:** 2026-11-08
- **Context:** The per-user cap has to hold under concurrency. If a user's cap is 4, two parallel
  requests can each count "2 already held", both see room, and both add 2 more, for 6 in total. No
  single-row constraint can see across those requests.
- **Options considered:**
  - Count holds and orders, then insert: races under READ COMMITTED, exactly as above.
  - `SELECT … FOR UPDATE` on the user row: serialises everything that user does, and that row
    belongs to the identity module.
  - SERIALIZABLE isolation: correct, but it forces retries and is harder to reason about.
  - A counter row per (event, user).
- **Decision:** I use a `user_event_allowance(event_id, user_id, used)` table with `CHECK (used >= 0)`.
  In the same transaction as the hold, I run
  `UPDATE … SET used = used + n WHERE used + n <= limit`. Zero rows updated means `LIMIT_EXCEEDED`.
  Releases and expiries decrement the counter. The Lua strategy keeps the same counter as a Redis key,
  checked inside the script.
- **Why:** A conditional UPDATE does the check and the increment in one atomic step. Postgres locks
  the row, makes the second request wait, and re-checks the WHERE against the new value. Requests only
  contend for the same user and event, so this doesn't slow the drop down for anyone else.
- **How I'd know it was wrong:** The concurrency test shows a user ending up over the cap. Or the
  invariant check finds `used` drifting from the user's real active holds and orders, probably
  because some release path forgot to decrement.

### D-006 Name-based UUIDs for seed data (an exception to D-002)
- **Date:** 2026-11-08
- **Context:** The seed loader has to be idempotent: running it twice must not create a second venue.
  Sections, seats and tiers have natural unique keys, but venues and events don't, so a second run
  couldn't tell it had already created them. The k6 load tests (M2.4) also need to know seat ids in
  advance.
- **Options considered:** name-based UUIDs for seed rows; a V2 migration adding unique `slug`
  columns to venues and events (ids stay random v4); looking rows up by name before inserting, with no
  constraint behind it.
- **Decision:** Every seed row gets a version 3 UUID made from its name, for example
  `UUID.nameUUIDFromBytes("stampede-seed:seat:demo-arena:FL-L:A:1")`. Inserts use
  `ON CONFLICT (id) DO NOTHING`, then the loader reads everything back and fails, rolling back, if the
  database doesn't match the file. Rows the app creates at runtime still use random v4 ids (D-002).
- **Why:** The same file gives the same ids on every machine, so loading is naturally idempotent with
  no schema change, and load tests can target known seats. Looking up by name has no constraint behind
  it, so it can still duplicate rows. The costs: seed ids can be guessed (fine, since seed data is
  public demo data), v3 uses MD5 (fine for naming rows, never for security), and renaming a slug or
  section code changes every id under it.
- **How I'd know it was wrong:** I need to edit loaded venues in place (for example, the venue editor in
  O5) and keep finding myself fighting fixed ids. Or real, non-seed data starts depending on the
  `stampede-seed:` naming scheme.

### D-007 Module APIs as named interfaces, with an enforced dependency table
- **Date:** 2026-11-08
- **Context:** D-001 says modules talk only through public APIs or events. Spring Modulith can check
  that, but I have to choose what counts as a module's public API, and which module may depend on
  which. Some modules should only *react* to another module's events, never call it.
- **Options considered:** (A) Modulith's default: a module's top-level package is its API and
  subpackages are internal; (B) explicit `api` and `events` subpackages marked `@NamedInterface`,
  with nothing public in the top-level package; (C) the top-level package as the API plus one
  `events` named interface.
- **Decision:** Option B. `<module>.api` holds what other modules may call, `<module>.events` holds
  the events it publishes. Everything else (including `inventory.seed`) is internal. Each module's
  `package-info.java` declares `@ApplicationModule(allowedDependencies = ...)` and `ModularityTest`
  runs `ApplicationModules.verify()`. The full table is enforced from day one:

  | Module | May call (`::api`) | May listen to (`::events`) |
  |---|---|---|
  | identity | none | none |
  | waitingroom | identity | none |
  | inventory | waitingroom | none |
  | payments | none | none |
  | ticketing | identity | none |
  | booking | inventory, payments, ticketing | inventory, payments |
  | realtime | none | inventory, waitingroom, booking |
  | control | waitingroom, inventory, booking, payments, ticketing | waitingroom, inventory, booking, payments, ticketing |

  The table is a DAG. Booking orchestrates the saga by calling inventory, payments and ticketing and
  reacting to their events; none of them depend on booking. Payments gets the order id and amount as
  arguments, and control drives chaos settings through payments' API, so payments depends on nothing.
  An explicit `allowedDependencies = {}` means "nothing allowed"; leaving the attribute out would mean
  "anything allowed", so every module declares it.
- **Why:** With a single public package, a dependency is all-or-nothing, so "realtime may only listen
  to inventory" would be a comment. Named interfaces let the test tell calling apart from listening.
  The cost is a bit of ceremony (a `package-info` per interface) and remembering that event classes
  live in the publisher's `events` package, so a listener depends on the publisher.
- **Limit: table ownership is a convention.** Modulith analyses Java type references, not SQL. If
  booking runs `SELECT ... FROM event_seats` through JdbcClient, the test can't see it. Each module's
  `package-info` lists the tables it owns, and other modules must go through its API instead.
- **How I'd know it was wrong:** I keep adding allowances just to get features through, or I invent
  awkward events purely to avoid a "may call" edge. Or a code review finds a module querying another
  module's tables, which means the convention needs a check of its own (for example, separate DB
  schemas per module).

### D-008 Auth: short-lived JWTs, rotating refresh tokens, one lock row per session
- **Date:** 2026-11-08
- **Context:** PRD 11 asks for short-lived JWTs with rotating refresh tokens and bcrypt or Argon2.
  Three API instances must verify tokens without sharing sessions, and a stolen refresh token must
  not give an attacker a session that outlives the user's.
- **Options considered:** Spring's OAuth2 resource server vs jjwt plus a hand-written filter; HS256
  vs an asymmetric key pair; bcrypt vs Argon2id; refresh token in an httpOnly cookie vs the response
  body; strict reuse detection vs a grace window for parallel refreshes.
- **Decision:**
  - Access tokens: HS256 JWTs (sub = user id, role, iss, iat, exp, jti), 15 minutes, signed with
    `STAMPEDE_JWT_SECRET` (at least 32 bytes; the app won't start without it). Verified by Spring's
    `BearerTokenAuthenticationFilter`, with the algorithm pinned, issuer and exp required, and 30 s
    of clock skew allowed.
  - Passwords: bcrypt cost 12, at least 12 characters, at most 72 UTF-8 bytes (bcrypt silently
    ignores the rest). Login gives the same answer for an unknown email and a wrong password, and
    compares against a dummy hash so timing doesn't tell them apart.
  - Refresh tokens: 32 random bytes, stored only as SHA-256, sent only in an httpOnly, Secure,
    SameSite=Strict cookie on `/auth`, with a required `X-Requested-With` header as a CSRF guard.
    7 days, renewed on every refresh, never past a 30-day cap per login.
  - Every refresh consumes its token and issues a child. Presenting a used token again (reuse)
    revokes the whole login session: we can't tell the real user from the thief, so both must log
    in again. This is strict: two tabs refreshing at the same moment also log the user out, so the
    frontend funnels refreshes through one shared call (M0.7).
  - A `refresh_token_families` table holds one row per login session (its 30-day cap and its
    revocation), and that row is the session's lock: every refresh and every revocation starts with
    `SELECT ... FROM refresh_token_families WHERE id = ? FOR UPDATE`.
  - 401, 403 and auth errors are problem+json with stable codes (PRD 10).
- **Why the family table exists:** the first version had only `refresh_tokens`, with the revocation
  on each token row, and the concurrency tests found two bugs in it:
  1. *Deadlock.* When 20 requests refresh the same token, one wins and 19 detect reuse and revoke
     the family with `UPDATE refresh_tokens SET revoked_at = now() WHERE family_id = ?`. That
     statement locks the family's rows in whatever order it scans them, so two revokers could each
     lock one row and wait for the other's. Postgres broke the cycle by killing one: a 500, in about
     one run in five.
  2. *Logout could miss a token.* A refresh consumes token P (locking P) while a logout runs that same
     UPDATE. The logout's statement only sees P, waits for P's lock, and meanwhile the refresh inserts
     child C and commits. The logout then revokes P and returns 204, but C was never in its snapshot
     and stays live. An attacker refreshing at the moment the user logs out would keep a session.

  With one lock row per family, everything that touches a family queues on that one row and runs one
  at a time. Each holder re-reads the token after getting the lock, so it sees what the previous
  holder committed. Revoking becomes a single-row update: a racing refresh either commits first (and
  its child belongs to a family that is then revoked, so it dies with it) or waits and sees the
  revocation. No transaction locks rows of two families, so there is no lock order to get wrong. The
  same idea as sorting seat ids before `FOR UPDATE` in the pessimistic strategy: make every
  competitor queue for the same thing first.

  Two details matter. It relies on READ COMMITTED (Postgres's default): the lock decides who goes
  next, but seeing the previous holder's writes depends on each statement after the lock taking a
  fresh snapshot. And under the lock, rotation also checks the family's own 30-day cap (a token
  never outlives its session) and consumes with `WHERE used_at IS NULL`, checking that exactly one
  row changed, so a future code path that forgets the lock fails loudly instead of consuming a
  token twice. A token that is both used and expired still counts as reuse and revokes the session.
  A correctness review found no bug in this design, but showed the original logout race test could
  not catch a broken logout (reuse detection revoked the family anyway); it now races exactly one
  refresh against one logout, and fails all 30 runs if logout is disabled.
- **Trade-offs:** an access token stays valid for up to 15 minutes after logout or role change (it is
  checked by signature only). Anyone with the HS256 secret can mint tokens, which is fine while only
  our own instances hold it. The refresh cookie needs the API and frontend to be same-site (M0.7
  proxy, M7.1 deployment). bcrypt cost 12 makes login slow on purpose (M2.4 logs in during k6 setup).
  `refresh_tokens` grows forever until a cleanup job deletes expired families (not built yet).
  Requests for one session queue on its lock while holding a DB connection; rate limiting (M4.3)
  is the defence against a flood for one session.
- **How I'd know it was wrong:** users report being logged out with several tabs open (reuse
  detection firing on benign races more than expected); the family lock shows up as a hotspot (it
  shouldn't, since only one user's session queues on it); or I need to revoke access tokens
  immediately (that would mean a denylist or much shorter access tokens).

### D-009 A small shared module for types every module needs
- **Date:** 2026-11-08
- **Context:** Almost every module will need to know who is calling, and every module returns errors
  with the stable codes from PRD 10. D-007 lets only waitingroom and ticketing depend on identity.
- **Options considered:** a `CurrentUser` type in `identity::api` (every module would need an
  identity allowance, rewriting much of D-007's table); a `shared` module; controllers reading the
  raw JWT themselves (no shared type, but claim parsing copied everywhere and tied to JWTs).
- **Decision:** A `shared` module with two named interfaces: `shared.security` (`CurrentUser`,
  `Role`) and `shared.error` (`ErrorCode`, `Problems`, `ApiException`). Identity's token converter
  puts a `CurrentUser` into the security context, so controllers in any module take
  `@AuthenticationPrincipal CurrentUser` without depending on identity. `shared` itself has
  `allowedDependencies = {}`, and every module lists `"shared :: security", "shared :: error"`
  explicitly. Rule: only types that every module needs go in shared.
- **Why:** It keeps the D-007 graph unchanged and gives M0.6 a home for error handling. Probes showed
  how Modulith 1.4 treats it: types in shared's subpackages are internal unless marked as named
  interfaces; allowing just `"shared"` only covers its top-level package; `"shared :: *"` or naming
  each interface works. I chose explicit names because they are easy to search for and match how
  D-007 is written. `@ApplicationModule(type = OPEN)` also worked, but exposes every type in shared,
  which would let it quietly become a junk drawer.
- **How I'd know it was wrong:** shared starts collecting module-specific types (anything only one or
  two modules use belongs in that module's api), or a change to shared keeps forcing changes in many
  modules at once.
