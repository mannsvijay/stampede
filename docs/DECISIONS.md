# Design decisions

Write these yourself, in your own words. Each one is an interview answer you've already rehearsed.

## Template
### D-000 Title
- **Date:**
- **Context:** what problem forced a choice
- **Options considered:** at least two
- **Decision:**
- **Why:** the trade-off in one or two sentences
- **How I'd know it was wrong:** a measurement or symptom

---

### D-001 Modular monolith instead of microservices
- **Date:** 2026-11-07
- **Context:** I'm one person with about twelve weeks. The hard part of this project is contention:
  many buyers racing for the same seats. Splitting the system into services is a different problem.
- **Options considered:** microservices; a plain monolith with no internal boundaries; a modular
  monolith with enforced boundaries.
- **Decision:** One Spring Boot app split into eight modules (identity, inventory, booking, payments,
  ticketing, waitingroom, realtime, control). Modules talk only through each other's public API package
  or through events, and a Spring Modulith test fails the build if a module reaches into another.
  I run it as three identical instances behind Nginx.
- **Why:** Microservices would cost me network calls, distributed transactions and deployment work
  without teaching me anything more about contention. A plain monolith turns into a tangle. With
  enforced modules, I get clean boundaries now and could still split a module out later.
- **How I'd know it was wrong:** One module needs to scale differently from the rest. For example,
  waitingroom or realtime saturates the CPU while booking sits idle, so I'm forced to scale everything
  to scale one thing. Or the Modulith test keeps pushing me into workarounds that make the code worse.

### D-002 UUID v4 ids, generated by the app
- **Date:** 2026-11-08
- **Context:** Every table needs a primary key type, and I wanted one type everywhere.
- **Options considered:** bigint identity; UUID v4; UUID v7 (time-ordered); a hybrid with bigint for
  internal tables and UUIDs for public ones.
- **Decision:** UUID v4 everywhere. The app creates ids with `UUID.randomUUID()`, and
  `gen_random_uuid()` is the column default for rows inserted straight from SQL.
- **Why:** In the Redis-first strategy, the Lua script creates a hold before Postgres knows about it,
  so the id must exist before the insert. UUIDs also can't be guessed in URLs, so `/orders/1042`
  doesn't leak my sales volume. The cost is 16 bytes per id, and random values spread inserts across
  the index instead of appending at the end.
- **How I'd know it was wrong:** The benchmarks show index bloat or slow inserts on the busy tables
  (holds, order_items, outbox). Then I'd switch to UUID v7, which needs no migration because the
  column type stays `uuid`.

### D-003 Seat states narrowed to AVAILABLE / HELD / SOLD
- **Date:** 2026-11-08
- **Context:** The PRD's seat diagram also has CHECKED_IN and TRANSFERRED. But a checked-in or
  transferred seat is still sold. Those two states describe the ticket, not the seat.
- **Options considered:** keep all five states on `event_seats`, as the PRD draws it; keep only
  AVAILABLE/HELD/SOLD on the seat and move the rest to tickets.
- **Decision:** `event_seats.status` is AVAILABLE, HELD or SOLD. Tickets have ISSUED, CHECKED_IN or
  REVOKED. A transfer keeps the same ticket row and bumps its version and holder.
- **Why:** With five seat states, every "is this seat sold?" query and every invariant (for example,
  "every sold seat has a paid order") has to remember that three values mean sold. Keeping the seat to
  the three states that matter for contention keeps the hot path and the checks simple.
- **How I'd know it was wrong:** Seat-map or gate views keep joining tickets just to show a seat's
  state, or I find a rule that genuinely depends on the seat, not the ticket, being checked in.

### D-004 Seat transition guard in code, not a database trigger
- **Date:** 2026-11-08
- **Context:** The PRD says transitions are guarded "in code and in the database". A CHECK constraint
  can only limit which values are allowed. Stopping an invalid move such as SOLD to HELD in the
  database would need a `BEFORE UPDATE` trigger on `event_seats`.
- **Options considered:** a trigger that rejects transitions not in the diagram; a state machine
  class in code (M1.1) only, plus database constraints on the data itself.
- **Decision:** The guard lives in code. The database still enforces what it can check on a single
  row: the CHECK that ties status to `hold_id`/`order_id` (HELD needs a hold, SOLD needs an order), and
  the unique partial index on active order items.
- **Why:** `event_seats` is the hottest write path in the system. A trigger would run on every hold
  under contention and skew the benchmark that compares strategies. The trade-off is that code
  bypassing the state machine could make a bad transition without the database objecting. The index
  and the invariant checker after every test are my safety net.
- **How I'd know it was wrong:** The invariant checker catches a bad transition that came from code
  skipping the guard. Or I measure the trigger and its cost is negligible, in which case I'd add it.

### D-005 Per-user ticket cap via a counter row
- **Date:** 2026-11-08
- **Context:** The per-user cap has to hold under concurrency. If a user's cap is 4, two parallel
  requests can each count "2 already held", both see room, and both add 2 more, for 6 in total. No
  single-row constraint can see across those requests.
- **Options considered:**
  - Count holds and orders, then insert: races under READ COMMITTED, exactly as above.
  - `SELECT … FOR UPDATE` on the user row: serialises everything that user does, and that row
    belongs to the identity module.
  - SERIALIZABLE isolation: correct, but it forces retries and is harder to reason about.
  - A counter row per (event, user).
- **Decision:** I use a `user_event_allowance(event_id, user_id, used)` table with `CHECK (used >= 0)`.
  In the same transaction as the hold, I run
  `UPDATE … SET used = used + n WHERE used + n <= limit`. Zero rows updated means `LIMIT_EXCEEDED`.
  Releases and expiries decrement the counter. The Lua strategy keeps the same counter as a Redis key,
  checked inside the script.
- **Why:** A conditional UPDATE does the check and the increment in one atomic step. Postgres locks
  the row, makes the second request wait, and re-checks the WHERE against the new value. Requests only
  contend for the same user and event, so this doesn't slow the drop down for anyone else.
- **How I'd know it was wrong:** The concurrency test shows a user ending up over the cap. Or the
  invariant check finds `used` drifting from the user's real active holds and orders, probably
  because some release path forgot to decrement.
- **Implemented in M1.4 (D-016):** one upsert inside the strategy's transaction (it also creates the
  row on a user's first hold); every release reason decrements; harness invariant I8 checks the
  counter against active holds after every round.

### D-006 Name-based UUIDs for seed data (an exception to D-002)
- **Date:** 2026-11-08
- **Context:** The seed loader has to be idempotent: running it twice must not create a second venue.
  Sections, seats and tiers have natural unique keys, but venues and events don't, so a second run
  couldn't tell it had already created them. The k6 load tests (M2.4) also need to know seat ids in
  advance.
- **Options considered:** name-based UUIDs for seed rows; a V2 migration adding unique `slug`
  columns to venues and events (ids stay random v4); looking rows up by name before inserting, with no
  constraint behind it.
- **Decision:** Every seed row gets a version 3 UUID made from its name, for example
  `UUID.nameUUIDFromBytes("stampede-seed:seat:demo-arena:FL-L:A:1")`. Inserts use
  `ON CONFLICT (id) DO NOTHING`, then the loader reads everything back and fails, rolling back, if the
  database doesn't match the file. Rows the app creates at runtime still use random v4 ids (D-002).
- **Why:** The same file gives the same ids on every machine, so loading is naturally idempotent with
  no schema change, and load tests can target known seats. Looking up by name has no constraint behind
  it, so it can still duplicate rows. The costs: seed ids can be guessed (fine, since seed data is
  public demo data), v3 uses MD5 (fine for naming rows, never for security), and renaming a slug or
  section code changes every id under it.
- **How I'd know it was wrong:** I need to edit loaded venues in place (for example, the venue editor in
  O5) and keep finding myself fighting fixed ids. Or real, non-seed data starts depending on the
  `stampede-seed:` naming scheme.

### D-007 Module APIs as named interfaces, with an enforced dependency table
- **Date:** 2026-11-08
- **Context:** D-001 says modules talk only through public APIs or events. Spring Modulith can check
  that, but I have to choose what counts as a module's public API, and which module may depend on
  which. Some modules should only *react* to another module's events, never call it.
- **Options considered:** (A) Modulith's default: a module's top-level package is its API and
  subpackages are internal; (B) explicit `api` and `events` subpackages marked `@NamedInterface`,
  with nothing public in the top-level package; (C) the top-level package as the API plus one
  `events` named interface.
- **Decision:** Option B. `<module>.api` holds what other modules may call, `<module>.events` holds
  the events it publishes. Everything else (including `inventory.seed`) is internal. Each module's
  `package-info.java` declares `@ApplicationModule(allowedDependencies = ...)` and `ModularityTest`
  runs `ApplicationModules.verify()`. The full table is enforced from day one:

  | Module | May call (`::api`) | May listen to (`::events`) |
  |---|---|---|
  | identity | none | none |
  | waitingroom | identity | none |
  | inventory | waitingroom | none |
  | payments | none | none |
  | ticketing | identity | none |
  | booking | inventory, payments, ticketing | inventory, payments |
  | realtime | none | inventory, waitingroom, booking |
  | control | waitingroom, inventory, booking, payments, ticketing | waitingroom, inventory, booking, payments, ticketing |

  The table is a DAG. Booking orchestrates the saga by calling inventory, payments and ticketing and
  reacting to their events; none of them depend on booking. Payments gets the order id and amount as
  arguments, and control drives chaos settings through payments' API, so payments depends on nothing.
  An explicit `allowedDependencies = {}` means "nothing allowed"; leaving the attribute out would mean
  "anything allowed", so every module declares it.
- **Why:** With a single public package, a dependency is all-or-nothing, so "realtime may only listen
  to inventory" would be a comment. Named interfaces let the test tell calling apart from listening.
  The cost is a bit of ceremony (a `package-info` per interface) and remembering that event classes
  live in the publisher's `events` package, so a listener depends on the publisher.
- **Limit: table ownership is a convention.** Modulith analyses Java type references, not SQL. If
  booking runs `SELECT ... FROM event_seats` through JdbcClient, the test can't see it. Each module's
  `package-info` lists the tables it owns, and other modules must go through its API instead.
- **How I'd know it was wrong:** I keep adding allowances just to get features through, or I invent
  awkward events purely to avoid a "may call" edge. Or a code review finds a module querying another
  module's tables, which means the convention needs a check of its own (for example, separate DB
  schemas per module).

### D-008 Auth: short-lived JWTs, rotating refresh tokens, one lock row per session
- **Date:** 2026-11-08
- **Context:** PRD 11 asks for short-lived JWTs with rotating refresh tokens and bcrypt or Argon2.
  Three API instances must verify tokens without sharing sessions, and a stolen refresh token must
  not give an attacker a session that outlives the user's.
- **Options considered:** Spring's OAuth2 resource server vs jjwt plus a hand-written filter; HS256
  vs an asymmetric key pair; bcrypt vs Argon2id; refresh token in an httpOnly cookie vs the response
  body; strict reuse detection vs a grace window for parallel refreshes.
- **Decision:**
  - Access tokens: HS256 JWTs (sub = user id, role, iss, iat, exp, jti), 15 minutes, signed with
    `STAMPEDE_JWT_SECRET` (at least 32 bytes; the app won't start without it). Verified by Spring's
    `BearerTokenAuthenticationFilter`, with the algorithm pinned, issuer and exp required, and 30 s
    of clock skew allowed.
  - Passwords: bcrypt cost 12, at least 12 characters, at most 72 UTF-8 bytes (bcrypt silently
    ignores the rest). Login gives the same answer for an unknown email and a wrong password, and
    compares against a dummy hash so timing doesn't tell them apart.
  - Refresh tokens: 32 random bytes, stored only as SHA-256, sent only in an httpOnly, Secure,
    SameSite=Strict cookie on `/auth`, with a required `X-Requested-With` header as a CSRF guard.
    7 days, renewed on every refresh, never past a 30-day cap per login.
  - Every refresh consumes its token and issues a child. Presenting a used token again (reuse)
    revokes the whole login session: we can't tell the real user from the thief, so both must log
    in again. This is strict: two tabs refreshing at the same moment also log the user out, so the
    frontend funnels refreshes through one shared call (M0.7).
  - A `refresh_token_families` table holds one row per login session (its 30-day cap and its
    revocation), and that row is the session's lock: every refresh and every revocation starts with
    `SELECT ... FROM refresh_token_families WHERE id = ? FOR UPDATE`.
  - 401, 403 and auth errors are problem+json with stable codes (PRD 10).
- **Why the family table exists:** the first version had only `refresh_tokens`, with the revocation
  on each token row, and the concurrency tests found two bugs in it:
  1. *Deadlock.* When 20 requests refresh the same token, one wins and 19 detect reuse and revoke
     the family with `UPDATE refresh_tokens SET revoked_at = now() WHERE family_id = ?`. That
     statement locks the family's rows in whatever order it scans them, so two revokers could each
     lock one row and wait for the other's. Postgres broke the cycle by killing one: a 500, in about
     one run in five.
  2. *Logout could miss a token.* A refresh consumes token P (locking P) while a logout runs that same
     UPDATE. The logout's statement only sees P, waits for P's lock, and meanwhile the refresh inserts
     child C and commits. The logout then revokes P and returns 204, but C was never in its snapshot
     and stays live. An attacker refreshing at the moment the user logs out would keep a session.

  With one lock row per family, everything that touches a family queues on that one row and runs one
  at a time. Each holder re-reads the token after getting the lock, so it sees what the previous
  holder committed. Revoking becomes a single-row update: a racing refresh either commits first (and
  its child belongs to a family that is then revoked, so it dies with it) or waits and sees the
  revocation. No transaction locks rows of two families, so there is no lock order to get wrong. The
  same idea as sorting seat ids before `FOR UPDATE` in the pessimistic strategy: make every
  competitor queue for the same thing first.

  Two details matter. It relies on READ COMMITTED (Postgres's default): the lock decides who goes
  next, but seeing the previous holder's writes depends on each statement after the lock taking a
  fresh snapshot. And under the lock, rotation also checks the family's own 30-day cap (a token
  never outlives its session) and consumes with `WHERE used_at IS NULL`, checking that exactly one
  row changed, so a future code path that forgets the lock fails loudly instead of consuming a
  token twice. A token that is both used and expired still counts as reuse and revokes the session.
  A correctness review found no bug in this design, but showed the original logout race test could
  not catch a broken logout (reuse detection revoked the family anyway); it now races exactly one
  refresh against one logout, and fails all 30 runs if logout is disabled.
- **Trade-offs:** an access token stays valid for up to 15 minutes after logout or role change (it is
  checked by signature only). Anyone with the HS256 secret can mint tokens, which is fine while only
  our own instances hold it. The refresh cookie needs the API and frontend to be same-site (M0.7
  proxy, M7.1 deployment). bcrypt cost 12 makes login slow on purpose (M2.4 logs in during k6 setup).
  `refresh_tokens` grows forever until a cleanup job deletes expired families (not built yet).
  Requests for one session queue on its lock while holding a DB connection; rate limiting (M4.3)
  is the defence against a flood for one session.
- **How I'd know it was wrong:** users report being logged out with several tabs open (reuse
  detection firing on benign races more than expected); the family lock shows up as a hotspot (it
  shouldn't, since only one user's session queues on it); or I need to revoke access tokens
  immediately (that would mean a denylist or much shorter access tokens).

### D-009 A small shared module for types every module needs
- **Date:** 2026-11-08
- **Context:** Almost every module will need to know who is calling, and every module returns errors
  with the stable codes from PRD 10. D-007 lets only waitingroom and ticketing depend on identity.
- **Options considered:** a `CurrentUser` type in `identity::api` (every module would need an
  identity allowance, rewriting much of D-007's table); a `shared` module; controllers reading the
  raw JWT themselves (no shared type, but claim parsing copied everywhere and tied to JWTs).
- **Decision:** A `shared` module with two named interfaces: `shared.security` (`CurrentUser`,
  `Role`) and `shared.error` (`ErrorCode`, `Problems`, `ApiException`). Identity's token converter
  puts a `CurrentUser` into the security context, so controllers in any module take
  `@AuthenticationPrincipal CurrentUser` without depending on identity. `shared` itself has
  `allowedDependencies = {}`, and every module lists `"shared :: security", "shared :: error"`
  explicitly. Rule: only types that every module needs go in shared, plus the internal web plumbing
  that applies those types to every module (amended by D-010): the application-wide problem+json
  handler, the `/error` controller and the OpenAPI error documentation, in the internal package
  `shared.web`. That package is not a named interface, so no module can reference it; Spring finds it
  by component scanning.
- **Why:** It keeps the D-007 graph unchanged and gives M0.6 a home for error handling. Probes showed
  how Modulith 1.4 treats it: types in shared's subpackages are internal unless marked as named
  interfaces; allowing just `"shared"` only covers its top-level package; `"shared :: *"` or naming
  each interface works. I chose explicit names because they are easy to search for and match how
  D-007 is written. `@ApplicationModule(type = OPEN)` also worked, but exposes every type in shared,
  which would let it quietly become a junk drawer.
- **How I'd know it was wrong:** shared starts collecting module-specific types (anything only one or
  two modules use belongs in that module's api), or a change to shared keeps forcing changes in many
  modules at once.

### D-010 Event read API, one problem+json handler, and a committed OpenAPI spec (DRAFT)
- **Date:** 2026-11-09
- **Context:** M0.6 adds the first public read endpoints (`GET /events`, `GET /events/{id}`) and
  replaces identity's scoped error handler with one for the whole app. M0.7 generates the TypeScript
  client from the OpenAPI spec, and PRD 10 says the spec is the source of truth, so the contract has
  to be fixed somewhere reviewable before the frontend starts.
- **Options considered:**
  - Spec: generate it from code with springdoc; write it by hand first and check the code against it
    (needs a contract-test library); generate it but commit the output and fail a test on drift.
  - Handler location: an internal `shared.web` package; a new `platform` module; the root
    `com.stampede` package (which Modulith doesn't verify at all).
  - Error codes: one central `ErrorCode` enum in shared; per-module code enums behind an interface.
  - Pagination: keyset cursor now; a hard cap now and a cursor later.
  - Availability counts (available/held/sold) in the responses: now; leave them to realtime.
- **Decision:**
  - **OpenAPI:** springdoc-openapi 2.10.0 (`-api` artifact, no Swagger UI; built against Spring Boot
    3.5.16, while the 3.x line targets Boot 4). The generated spec is committed at `docs/openapi.json`,
    and `OpenApiSpecTest` fails if the code generates anything else. M0.7 builds the client from the
    committed file, so every contract change shows up in a diff. `/v3/api-docs` is off unless the
    `openapi` profile is active. Errors are documented from the code: `@ErrorResponses({...})` on a
    controller method lists its codes, and each becomes a problem+json response under that code's own
    status, plus `500 INTERNAL_ERROR` on every operation. Response-only schemas mark every property
    required, because Jackson always writes every field (otherwise every generated TypeScript field
    would be optional). The server URL is a fixed `/` so the file doesn't change with the test's
    random port.
  - **Error handler:** `ApiExceptionHandler` in internal `shared.web`, extending Spring's
    `ResponseEntityExceptionHandler`, so every standard MVC error (404 route, 405, 415, malformed
    parameter) passes through one method that adds our `code` and a fixed message. Anything unexpected
    is a 500 with a generic message and an `errorId`; the exception goes only to the log. Security
    exceptions thrown inside a controller are rethrown so Spring Security still answers 401/403. A
    `ProblemErrorController` replaces Boot's `/error` page, which handles errors outside MVC (filters,
    `sendError`) and uses only the status. D-009's wording was amended to allow this.
  - **Error codes:** one central enum. New: `EVENT_NOT_FOUND`, `NOT_FOUND`, `METHOD_NOT_ALLOWED`,
    `UNSUPPORTED_MEDIA_TYPE`, `REQUEST_FAILED`, `INTERNAL_ERROR`.
  - **Read endpoints:** owned by inventory (D-007), in internal `inventory.catalog` with JdbcClient.
    The list is `{items, serverTime}`, capped at 100, ordered by drop time; it hides DRAFT, ENDED and
    already-started events. A DRAFT id gives 404, like an unknown id. The detail is read in one SQL
    statement. No availability counts.
  - **Demo times:** a dev-only `demo-reschedule` profile moves the demo event's drop and start back to
    now + the seed file's offsets, only while it is SCHEDULED.
- **Why:**
  - Generating the spec means it can't fall out of date. Committing it and testing for drift means
    nobody changes it without seeing the change, which keeps "the spec is the source of truth" honest
    without hand-writing YAML.
  - `shared.web` keeps the handler next to the types it applies, without a module that exists for two
    classes, and it stays under Modulith's checks (unlike the root package).
  - One code enum mirrors PRD 10's single table and gives the client generator one list.
  - `items` in a wrapper object lets a cursor arrive later without breaking clients.
  - Counts are stale as soon as they are sent, and counting `event_seats` on every board refresh adds
    reads to the hottest table during a drop.
  - One SQL statement for the detail: under READ COMMITTED, each statement sees its own snapshot, so
    two separate queries could see the event and its tiers at different moments.
- **Trade-offs:**
  - The drift test needs its own application context with the `openapi` profile, so it starts its own
    containers.
  - An intended API change takes two steps: change the code, then copy `build/openapi/openapi.json`
    over `docs/openapi.json`.
  - Response fields are typed as always present, which stays true only while response records don't
    use `@JsonInclude(NON_NULL)`.
  - Shared now depends on springdoc and Spring Security classes (libraries, not modules).
  - Security runs before routing, so anonymous callers get 401 instead of 404/405 (documented in PRD 10).
- **How I'd know it was wrong:**
  - The drift test gets "fixed" by copying the file without anyone reading the diff, so the committed
    spec stops being a real review point.
  - `shared.web` starts collecting non-error infrastructure.
  - The 100-event cap is hit.
  - The board needs live counts before M5 exists.

### D-011 Frontend shell: tooling, generated client, and token handling (DRAFT)
- **Date:** 2026-11-09
- **Context:** M0.7 starts the frontend. It needs a typed client for the API whose contract is the
  committed `docs/openapi.json` (D-010), an auth layer that works with strict refresh-token reuse
  detection (D-008), and tooling that won't fight the custom design planned for M5 (PRD 7).
- **Options considered:**
  - Package manager: npm; pnpm.
  - Client generator: openapi-typescript + openapi-fetch (types only, tiny runtime); orval (generates
    TanStack Query hooks and mocks); @hey-api/openapi-ts (0.x, frequent breaking changes);
    openapi-generator (Java, verbose).
  - Generated client: committed with a regenerate-and-compare check; generated at build time.
  - Router: React Router; TanStack Router (type-safe params, more concepts); wouter (minimal).
  - Data fetching: TanStack Query; plain fetch in useEffect.
  - Styling: CSS Modules + CSS variables; Tailwind; a component library (conflicts with PRD 7).
  - Tests: Vitest + React Testing Library + jsdom + MSW; the same with hand-stubbed fetch.
  - URL scheme: app pages separate from API prefixes; the API behind `/api` with a proxy rewrite.
- **Decision:**
  - **Tools:** npm; openapi-typescript + openapi-fetch; React Router (library mode); TanStack Query;
    CSS Modules + `src/styles/tokens.css`; Vitest + React Testing Library + jsdom + MSW, with
    Playwright from M1.8.
  - **Generated types:** `src/api/schema.d.ts` is committed. `npm run gen:api` writes it and
    `npm run check:api` regenerates in memory and fails on a difference (CI in M0.8). Both use one
    script, so the check compares exactly what generation would write.
  - **Auth:** the access token lives only in memory. Our own `authFetch` (passed to openapi-fetch)
    adds the bearer token. On a 401 outside /auth, it refreshes once and retries once. Concurrent
    401s share one in-flight refresh, and a request whose token was already replaced retries without
    refreshing. Refreshes are serialised across tabs with the Web Locks API (`navigator.locks`),
    falling back to per-tab only where it is missing. Refresh and logout send `X-Requested-With`.
    Errors become `ApiError`, whose `code` is the generated union of codes.
  - **Clock:** countdowns use `offset = serverTime − midpoint(sent, received)`.
  - **URLs:** app pages are `/` and `/drops/:id`. The Vite dev proxy forwards only /auth, /events,
    /actuator and /v3, so the API and refresh cookie are same-origin.
  - **TypeScript is pinned to 5.9.3**, not 7.0. typescript-eslint 8.72 supports TypeScript
    `<6.1.0` and openapi-typescript 7.13 only `^5.x`, so npm can't install them alongside 7.
    **Revisit** when both support TypeScript 7.
  - **Supply chain:** exact versions only (`save-exact=true` in `.npmrc`). Every version is
    published at least 14 days before install, and `npm install --before=<date>` applies the same
    cutoff to transitive dependencies. package-lock.json is committed.
  - No login UI yet. It comes with the first page that needs a user (M1.8).
- **Why:**
  - **openapi-typescript:** generates only types, so the committed diff stays small and readable,
    and our auth logic is plain code we own rather than generator output.
  - **TanStack Query:** handles caching, ignoring stale responses, and refetching, which the board
    needs later anyway.
  - **CSS Modules + tokens:** no dependency, and M5 builds on the PRD 7 tokens directly.
  - **MSW:** tests run the real client code against fake responses. Unhandled requests fail the test
    explicitly; MSW's own 'error' mode only makes the fetch fail, which the UI can swallow.
  - **Shared and cross-tab refresh:** strict reuse detection (D-008) turns any two concurrent
    refreshes with the same cookie into a logout, so refreshes must queue both within a tab and
    across tabs.
  - **Separate app and API URLs:** a page reload never lands on the API, and the cookie path
    (`/auth`) needs no rewriting.
- **Trade-offs:**
  - Hooks are written by hand (one line each).
  - Exact pins and the 14-day rule mean security fixes arrive at least 14 days late. On 2026-11-09,
    `npm audit` reports 10 moderate findings from one advisory (minimatch, GHSA-g3hv-75wg-m249) in
    lint tooling only. `npm audit --omit=dev` reports 0. The fix (minimatch 11.0.1, published
    2026-10-27) wasn't 14 days old yet.
  - **Accepted (M0.8, 2026-11-09):** the minimatch finding is moderate, affects only dev-only lint
    tooling that never ships, and `npm audit --omit=dev` reports 0. CI reports it without failing
    (D-012). After 2026-11-10T22:26Z, add `"overrides": { "minimatch@10": "11.0.1" }` as its own
    commit (PLAN M0.7a), and remove the override once ESLint itself requires minimatch 11.

- **Date:** 2026-11-09
- **Context:** The M0 exit criterion needs `docker compose up` to run the system on a clean clone.
  Until M0.10 only Postgres, Redis and Mailpit ran in compose; the backend ran on the host with
  `./gradlew bootRun`. The backend needs secrets (database and Redis passwords, the JWT signing
  key), and the image must not contain them. Base images are third-party code, like npm packages
  and CI actions (D-011, D-012).
- **Options considered:**
  - Clean clone: one documented step (copy `.env.example` to `.env`, fill in the secrets); dev
    defaults in compose so no `.env` is needed; a script that generates `.env`.
  - Frontend: stays on `npm run dev`; a built bundle served by nginx in compose.
  - CI: no container check; a smoke job with a plain `docker compose build`; the same with the
    Buildx GitHub Actions layer cache (two more actions).
  - Runtime image: Temurin 21 JRE on Ubuntu noble; Temurin 21 JRE on Alpine; distroless Java 21;
    a custom `jlink` runtime.
  - Seeding: the backend service runs `seed,demo-reschedule`; a one-shot seed service.
- **Decision:**
  - Clean clone = copy `.env.example` to `.env` and fill in the secrets. Compose's `${VAR:?...}`

  - `backend/Dockerfile`, two stages. Build: `eclipse-temurin:21.0.12_8-jdk-noble`, Gradle wrapper,
    `bootJar` only (tests run in CI and locally, they need Docker). Runtime:

    2026-11-12).

  - It waits for healthy Postgres and Redis, binds `127.0.0.1:${BACKEND_PORT:-8080}`, and its
    healthcheck curls `/actuator/health` (curl is already in the runtime image).
  - Profiles: `seed,demo-reschedule` by default (both idempotent), overridden by
    `STAMPEDE_COMPOSE_PROFILES`; set but empty means no profiles. M7.1 reviews whether a deployed
    instance seeds.
  - The image name is left to compose (`<project>-backend`), so separate clones don't overwrite
    each other's image.
  - The frontend stays on `npm run dev` (Vercel in M7.1).
  - CI job `Compose smoke`: `.env` from the template with secrets generated by `openssl rand`,

  - People run `docker compose up` and `bootRun` together and hit port clashes often (then move
    the backend behind a compose profile and change the exit criterion's command).
  - A security scan of the runtime image keeps flagging packages the app never uses (then
    distroless or jlink).

### D-014 Seat state machine: shape, owner pointers, and jqwik (DRAFT)
- **Date:** 2026-11-10
- **Context:** M1.1 turns PRD 2's seat diagram into code (the guard D-004 put in code). The PRD
  leaves some things open: refund (SOLD to AVAILABLE) is drawn but marked P2, the database CHECK
  allows more pointer shapes than any transition needs, and it doesn't say what happens to
  `hold_id` once a seat is sold. Property tests need a new test dependency.
- **Options considered:**
  - Shape: a mutable entity; an immutable record whose transitions return a new seat.
  - SOLD: final; leaves SOLD through refund.
  - `hold_id` on sell: kept (a trail from seat to hold); cleared.
  - Property testing: jqwik 1.9.2, 1.9.3, 1.10.x; hand-rolled random loops in JUnit.
- **Decision:**
  - `inventory.seat.EventSeat`, an immutable record, internal to inventory (D-007): only inventory
    writes `event_seats`. Transitions: `hold` (AVAILABLE to HELD), `release`, `expire`, `failSaga`
    (HELD to AVAILABLE, the caller's hold must own the seat) and `sell` (HELD to SOLD, same check).
    Everything else throws `IllegalSeatTransitionException` with a reason (WRONG_STATE or
    HOLD_MISMATCH). It has no HTTP meaning; the inventory service maps it to SEAT_TAKEN or
    HOLD_EXPIRED when those endpoints exist (M1.4/M1.5).
  - The constructor enforces exactly `ck_event_seats_status_pointers`, so any row the database
    accepts can be loaded. Transitions only produce the strict shape: **the pointer on a seat is its
    current owner** (the hold while HELD, the order once SOLD). `sell` clears `hold_id`; history
    stays in `holds.seat_ids` and `order_items`.
  - **SOLD is final.** Refunding a sold seat is left out; adding it needs its own decision, and the
    "SOLD never goes back" property test would change to "only through refund". A payment that
    succeeds after its hold expired (PRD 6.4) refunds money but never touches a SOLD seat.
  - Every successful transition bumps `version` by 1 (the optimistic strategy compares it, M2.1).
  - Repeated or racing calls (expire after release) are rejected, not treated as no-ops.
  - Test dependency: `net.jqwik:jqwik:1.9.2`.
- **Why:** An immutable record can't be left half-changed by a rejected transition, and its
  constructor makes an invalid seat impossible to build. Clearing `hold_id` keeps "who owns this
  seat?" to one column per state, and stops it from quietly answering M1.5's open "how does an order
  link to its hold" question. jqwik 1.9.2 is built against JUnit Platform 1.11.3, older than the
  1.12.2 that Boot 3.5's BOM pins, so it runs on a newer platform (backwards compatible). 1.9.3 and
  1.10.x target Platform 1.13 and 1.14 and would be forced down to 1.12.2, which risks
  `NoSuchMethodError` at runtime. 1.9.3 only added a Kotlin API change. The trade-off of the guard
  in code (D-004) remains: the optimistic and Lua strategies repeat these rules in a WHERE clause or
  in Lua, and this class is the reference they must agree with.
- **How I'd know it was wrong:** refunds or seat kills become real requirements and SOLD can't stay
  final; or debugging keeps needing "which hold did this sold seat come from?" without joining
  `holds`; or a JUnit upgrade (Boot 4) leaves jqwik 1.9.2 behind, at which point move to 1.10.x.

### D-015 InventoryStrategy interface and one lock order (DRAFT)
- **Date:** 2026-11-10
- **Context:** PRD 6.2 needs three interchangeable strategies (pessimistic, optimistic, Redis-first)
  behind one interface. The Redis-first Lua script creates a hold before Postgres knows about it,
  and `event_seats.hold_id` has a foreign key to `holds`, so whoever creates the hold must insert the
  hold row. Several code paths will lock the same rows (hold, release, the expiry sweeper, the
  allowance counter from D-005, sell in M1.5), and two paths that lock in different orders can
  deadlock.
- **Options considered:**
  - Hold id: generated by the strategy; generated by the caller.
  - Results: exceptions for "seat taken"; sealed outcome values.
  - Expiry: the caller passes an `Instant`; the caller passes a `Duration` and the strategy computes
    the expiry from its own clock.
  - Lock order: sort ids in Java and lock in that order; let Postgres sort inside the locking
    statement (`ORDER BY seat_id FOR UPDATE`).
- **Decision:**
  - `inventory.strategy.InventoryStrategy` (internal, D-007): `hold(HoldRequest)` returns
    `Held(holdId, seatIds, expiresAt)` or `Rejected(SEAT_TAKEN | UNKNOWN_SEAT, offending seatIds)`;
    `release(eventId, holdId, reason)` returns `Released`, `NotActive`, `NotExpired` or `NotFound`.
    UNKNOWN_SEAT (a seat not in this event) takes precedence over SEAT_TAKEN. Exceptions are only for
    bugs and infrastructure failures.
  - The caller (the hold service, M1.4) generates a **new** `holdId` for every attempt (D-002). Reusing
    one is a programming error: the `holds` primary key rejects it with an exception and the
    transaction rolls back. Retrying the same buyer action safely is the job of an idempotency key at
    the API, not of the strategy.
  - `HoldRequest` rejects an empty list, duplicate seat ids and a `holdFor` under 1 s, so no strategy
    can forget those checks.
  - `HoldRequest` carries `Duration holdFor`. Each strategy computes the expiry from its own
    authoritative clock: Postgres `now()` for pessimistic and optimistic, Redis `TIME` for Lua. The
    database clock is authoritative for hold expiry; app servers' clocks are not. `now()` (the
    transaction's start time), not `statement_timestamp()`: time spent waiting for a seat lock comes
    off the hold, but row locks are released at commit, so a buyer only ever waits for another
    in-flight transaction (milliseconds), never for another buyer's 5-minute hold (a HELD seat is
    rejected at once). The cost is negligible, and `now()` keeps `expires_at - created_at` exactly the
    hold duration. If M2.4 shows long lock queues on hot seats, that is the `lock_timeout` question
    below, not a reason to change the clock.
  - `release(…, EXPIRED)` re-checks `expires_at <= now()` after locking the hold row and returns
    `NotExpired` otherwise: the sweeper picks holds before it has the lock, and a hold extended in
    between (PRD 6.3) must survive.
  - Both methods are `@Transactional` with the default REQUIRED propagation, so a caller that is
    already in a transaction pulls them into it. Callers must not do that: the sweeper and the hold
    service call the strategy from outside any transaction, one hold per call. (Joining several holds
    in one transaction would break the lock order below, and one failure would roll back all of them.)
  - The strategy inserts the `holds` row in the same transaction as the seat updates.
  - **Lock order, for every code path:** (1) the hold row, when the path starts from an existing hold
    (release, expiry, sell); (2) the event seats, in Postgres `seat_id` order, taken by one
    `SELECT … ORDER BY seat_id FOR UPDATE`; (3) the user's allowance row (M1.4). Creating a hold never
    waits on an existing hold row. The sweeper releases one hold per transaction.
  - Seat UPDATEs add `AND version = :oldVersion`; zero rows updated under the lock is a bug and
    throws. (Measured: with `FOR UPDATE` removed, this check alone turned every double-hold in the race
    tests into a rollback; with both removed, two buyers were told `Held` for the same seat.)
- **Why:**
  - Caller-generated ids and outcome values fit all three strategies: Lua returns a status code, not
    an exception, and "seat taken" is the normal result under contention.
  - A duration keeps two clocks out of one rule: if app servers computed expiry, clock skew between
    them would shorten or lengthen holds.
  - Postgres does the sort because the order that matters is the order rows are locked in, and that
    is Postgres's order. Java's `UUID.compareTo` compares signed longs and disagrees with Postgres's
    unsigned byte order (checked on Java 21 and Postgres 16: `9000…` sorts first in Java and last in
    Postgres). A Java sort followed by one `IN (…) FOR UPDATE` changes nothing: Postgres locks rows
    in the order its scan returns them, not the order of the IN list. Without `ORDER BY` that scan
    order is the physical or index order, which happens to be consistent but is not a rule anyone
    wrote down (the lock-order test stores rows out of `seat_id` order and fails without `ORDER BY`).
    Mixing a Java order in one path with `ORDER BY` in another is two orders, which can deadlock.
  - Locking several holds in one sweeper transaction would take seat locks hold by hold, not in one
    global seat order.
- **How I'd know it was wrong:** M1.3 or the k6 runs log deadlocks (`40P01`); or holds expire at
  visibly different times on different instances; or the optimistic strategy needs a third
  rejection the interface can't express (I'd add `CONTENDED` then); or under a drop, buyers queueing
  on one hot seat's lock use up the connection pool and stall other events (then add a bounded
  `lock_timeout` returning a rejection; measured in M2.4).

### D-016 Holds API, per-user cap in the strategy, expiry sweeper (DRAFT)
- **Date:** 2026-11-10
- **Context:** M1.4 puts holds behind HTTP: create (all-or-nothing, with the D-005 cap), cancel, and
  expiry after five minutes (PRD 6.3). PRD 10 names SEAT_TAKEN (with `takenAgoMs`), LIMIT_EXCEEDED
  and HOLD_EXPIRED but gives no statuses for most of them, the schema records no "taken at" time on
  a seat, D-015 gives every attempt a new hold id (so a retried POST can't be recognised by id), and
  the app will run as several instances (M6.1), each of which could sweep.
- **Options considered:**
  - `takenAgoMs`: a new `event_seats.status_changed_at` column; the owner's `created_at` read in the
    strategy's transaction; the same read after the transaction; null until M5.3.
  - Sweeper with several instances: every instance sweeps and duplicates are tolerated;
    `FOR UPDATE SKIP LOCKED` claims; ShedLock (new dependency and table); a Postgres advisory lock.
    Interval 1 s, 5 s or 30 s.
  - Retried POST after a timeout: accept SEAT_TAKEN; return the caller's existing hold if it covers
    exactly the requested seats; an `Idempotency-Key` now (pulled forward from M3.1).
  - Statuses: HOLD_EXPIRED 410 / 409 / 422; someone else's hold 404 / 403; own released or expired
    hold 204 / 410; own converted hold 409 / 404.
  - Where the cap is checked: in the hold service before the strategy; inside the strategy's
    transaction.
- **Decision:**
  - The cap lives **inside the strategy's transaction** (CLAUDE.md: enforced in every strategy).
    Step 4b, after the seat decision and before the hold insert, is one upsert:
    `INSERT … SELECT … WHERE :n <= per_user_limit ON CONFLICT DO UPDATE SET used = used + n WHERE
    used + n <= per_user_limit`. Zero rows = `Rejected(LIMIT_EXCEEDED)` with nothing written.
    Precedence UNKNOWN_SEAT > SEAT_TAKEN > LIMIT_EXCEEDED. The limit is read in that same statement.
  - Every release reason (RELEASED, EXPIRED, SAGA_FAILED) gives the seats back as step 11b, after
    the seat writes (lock order hold, seats, allowance; D-015). CONVERTED never reaches release, so
    bought seats keep counting. A missing row or a decrement below zero throws and rolls back.
  - `takenAgoMs`: the most recent owner's `created_at` (the hold if HELD, the order if SOLD),
    computed in SQL against `clock_timestamp()` while the seats are still locked. `Rejected` gains a
    `takenAgoMs` field, set exactly for SEAT_TAKEN.
  - Sweeper: **every instance sweeps**, fixed delay 5 s, each expired hold released in its own
    transaction through `release(…, EXPIRED)`. Candidates are read in pages of 500, oldest first,
    with keyset paging on `(expires_at, id)`, so holds whose release keeps failing (drift, which
    release refuses to touch) can't fill every page and starve healthy holds behind them (found by
    the correctness review). Neither the sweeper nor the hold service is `@Transactional`.
    `stampede.holds.sweeper.enabled/interval/batch-size`. SKIP LOCKED is the noted optimisation if
    duplicate work ever shows up (M6.1).
  - Retry: on SEAT_TAKEN, if the caller has an ACTIVE, unexpired hold on **exactly** the requested
    seats (array containment both ways), return it with 200 instead. M3.1 considers an
    `Idempotency-Key` for this endpoint too.
  - Statuses and codes: SEAT_TAKEN, LIMIT_EXCEEDED (with `limit`), SALE_NOT_OPEN and HOLD_CONVERTED
    are 409; HOLD_NOT_FOUND 404, for unknown ids and someone else's hold alike (no IDOR, no
    existence probe); DELETE of your own RELEASED or EXPIRED hold is 204 (idempotent); unknown seat
    ids are 400 VALIDATION_FAILED with a `seatIds` field error. HOLD_EXPIRED is **410 Gone**, added
    to `ErrorCode` in M1.5, the first task that returns it.
  - Sale window: holds only when `drop_at <= now()` and the event is SCHEDULED or LIVE; otherwise
    409 SALE_NOT_OPEN; DRAFT is 404 like GET /events/{id}. Checked by the service before the
    strategy, unlocked. Dev-only profile `demo-open-sale` sets the demo drop to one minute ago (and
    the start to its seed offset from now) so the demo can be held locally and by the M1.8 seat map.
  - Admission (M4.2): the controller will require an `X-Admission-Token` header verified through
    `waitingroom::api` (already an allowed dependency) before calling the service; 403 NOT_ADMITTED.
    Not in the spec until it is enforced.
- **Why:**
  - A cap checked outside the strategy's transaction is the race D-005 exists to prevent. The upsert
    also covers the user's first hold, before any counter row exists: when two first requests race,
    Postgres makes the second wait for the first insert and then takes the DO UPDATE path with its
    WHERE re-checked against the committed value.
  - Reading `created_at` needs no migration and no extra write on the hot path. The read happens only
    when a hold is rejected, under seat locks that keep the owner pointers stable, and reads (not
    locks) the hold or order row, so the lock order is untouched. `clock_timestamp()` because the
    owner may have committed after this transaction's `now()`.
  - Duplicate sweeping is already proven safe (`cancelAndExpiryOfTheSameHoldTakeTurns`, and
    `twoSweepersAtOnceExpireEveryHoldExactlyOnce`), costs no code or dependency, and the sweeper is
    the safety net behind Redis expiry (M2.2), so 5 s of lateness is fine.
  - Matching on the exact seat set fixes the common retry case with one read on the rejection path
    and no table. A deliberate duplicate request also gets the existing hold, which is harmless.
  - 404 for someone else's hold reveals nothing; 204 for an already-ended own hold matches what the
    caller wanted (not holding the seats); a converted hold is a real conflict the client must see.
- **Known limits (correctness review, accepted for now):** the sale-window and strategy read is
  unlocked, so a hold can commit just after an admin pauses the event, and once M2.3 lets an event
  change strategy, two requests could briefly use different strategies (re-check inside the
  strategy transaction then, e.g. in the upsert's SELECT on events). `takenAgoMs` for a SOLD seat
  is the order's creation time, not the moment it was sold. The `limit` in LIMIT_EXCEEDED comes from
  the unlocked pre-read. I8 treats `used > per_user_limit` as drift, which is wrong if an admin ever
  lowers a limit below existing holds. The in-flight retry (second POST waiting on the first's seat
  locks) is correct by reasoning but not tested.
- **How I'd know it was wrong:** I8 (allowance vs active holds) fires in the harness or the M1.7
  checker; the sweeper logs the same failed hold every tick (a drifted counter); multi-instance runs
  (M6.1) show lock waits on hold rows from duplicate sweeps; clients retrying with a *different*
  seat set double-hold, which needs the M3.1 idempotency key; or the unlocked sale-window check lets
  holds through on a paused event often enough to matter (move it into the strategy).

### D-017 Orders from holds: synchronous checkout in saga-shaped steps (DRAFT)
- **Date:** 2026-11-10
- **Context:** M1.5 turns an ACTIVE hold into a PAID order with a fake payment, before the M3 saga
  exists. `orders` had no link to its hold (M0.2 note). D-015 says strategy callers must not be
  `@Transactional`, and the Redis strategy (M2.2) can't join a database transaction anyway. D-014
  left open when `event_seats.order_id` is set. PRD 10 requires an `Idempotency-Key` on
  `POST /orders`, but the idempotency mechanism is M3.1. The unique index on active `order_items`
  means a PENDING order that is never finished blocks its seats from every other order.
- **Options considered:**
  - Order to hold link: `orders.hold_id` (NOT NULL, FK, UNIQUE); `holds.order_id` written by
    inventory; no column, matching `order_items` against `holds.seat_ids`.
  - Transactions: one per step; one booking transaction around everything; order and payment in one,
    sale separately.
  - `event_seats.order_id`: set only on sell; attached at order creation while the seat is HELD.
  - Idempotency-Key: wait for M3.1 and let the unique hold link make retries safe (loser gets 200
    with the existing order, or 409); require it now with the full PRD 6.4 semantics.
  - Fake payment: always succeeds; always succeeds and tests swap the provider bean; a config switch.
- **Decision:**
  - **V3 adds `orders.hold_id uuid NOT NULL`**, `fk_orders_hold (hold_id, event_id) → holds (id,
    event_id)` and `uq_orders_hold UNIQUE (hold_id)`. One hold has at most one order, ever (a
    cancelled order's hold is never reused: every hold attempt has a new id, D-015).
  - **One transaction per step**, in the order of the PRD 6.4 saga. The orchestrator
    `booking.checkout.CheckoutService` is not `@Transactional`:

    | Step | Owner (through its api) | Transaction | What it does |
    |---|---|---|---|
    | 0 HoldVerified | `inventory::api` `HoldService.checkoutHold` | none, unlocked read | caller's hold? ACTIVE and `expires_at > now()`? seat prices from the tiers |
    | 1 OrderCreated | booking `OrderWriter.createPending` | booking's own | PENDING order + active items; `uq_orders_hold` decides a race |
    | 2 Payment | `payments::api` `PaymentService.charge` | statement-level; provider call outside any transaction | payment row CREATED first, then SUCCEEDED or FAILED |
    | 3 SeatsSold | `inventory::api` `HoldService.sellForOrder` → `InventoryStrategy.sell` | the strategy's | lock hold row, re-check ACTIVE and not expired, lock seats `ORDER BY seat_id`, `EventSeat.sell`, hold CONVERTED; allowance untouched |
    | 4 PAID | booking `OrderWriter.markPaid` | booking's own | guarded PENDING → PAID, saga_state SEATS_SOLD; idempotent |

  - **`event_seats.order_id` is set only on sell** (D-014's strict shape stays: the pointer is the
    current owner). During PENDING the link is `orders.hold_id` plus `order_items`. A HELD seat
    never carries an order id, so "sell overwrites another order's pointer" can't happen; `sell` of a
    seat held by another hold is rejected by `EventSeat` (HOLD_MISMATCH).
  - **No Idempotency-Key until M3.1 (a deliberate deviation from PRD 10).** A concurrent `POST /orders`
    for the same hold, or a retry after a successful one, gets **200 with the existing order** as it
    is now (possibly still PENDING), instead of a second order or charge. A retry after a checkout that
    *failed* gets 410 HOLD_EXPIRED, because the failure released the hold (step 0 sees it RELEASED).
  - **Fake payment:** `payments.provider.PaymentProvider` (interface), `FakePaymentProvider` always
    succeeds. Tests use `@MockitoSpyBean` to decline or throw. A decline is 402 PAYMENT_FAILED: order
    CANCELLED, hold released with reason SAGA_FAILED (new `HoldService.releaseForFailedCheckout`).
  - **Status guards:** `OrderStatus` (PENDING → PAID/CANCELLED) and `PaymentStatus` (CREATED →
    SUCCEEDED/FAILED, SUCCEEDED → REFUNDED) are checked in code, and each UPDATE repeats the expected
    status in its WHERE clause.
  - **Errors:** HOLD_NOT_FOUND 404 (also for someone else's hold), HOLD_EXPIRED 410, PAYMENT_FAILED
    402, SEAT_TAKEN 409 (a seat still in another order's active items), ORDER_NOT_FOUND 404 (also for
    someone else's order). An unexpected failure is 500 INTERNAL_ERROR after compensation.
  - **Compensation in the orchestrator, best effort.** After step 1 every exit must leave the order
    PAID or CANCELLED. Compensation releases the hold **first**: that release takes the hold row
    lock, the same lock the sale takes, so its answer is definitive. If the hold is CONVERTED, the
    sale committed and the order is finished instead of undone. Then the order is cancelled (items
    inactive, which unblocks the seats), then the payment refunded. Each step is tried even if
    another fails; failures are logged with the order id and attached to the original exception.

    | Failure | Order ends | Seats / hold | Money | Response |
    |---|---|---|---|---|
    | Step 0 says not found / expired / converted | no new order | unchanged | none | 404 / 410 / 200 existing order |
    | Step 0 or 1 throws | nothing written (step 1 rolls back) | unchanged | none | 500 |
    | Step 1 hits `uq_orders_hold` | the other request's order | unchanged | none | 200 existing order |
    | Step 1 hits `uq_order_items_active_seat` | no new order | unchanged (blocked by another checkout: in flight, or crashed) | none | 409 SEAT_TAKEN ("try again shortly") |
    | Step 2 declined | CANCELLED | hold RELEASED, seats AVAILABLE, allowance back | payment FAILED | 402 (500 if the compensating release throws: the 402 promises released seats) |
    | Step 2 throws | CANCELLED | hold RELEASED, seats AVAILABLE, allowance back | payment left CREATED: outcome unknown, for M3 reconciliation | 500 |
    | Step 3 says hold expired / released | CANCELLED | nothing sold; an ACTIVE-but-expired hold is left to the sweeper | REFUNDED | 410 |
    | Step 3 throws, sale rolled back | CANCELLED | hold RELEASED, seats AVAILABLE, allowance back | REFUNDED | 500 |
    | Step 3 throws, sale had committed | PAID (finished) | SOLD, hold CONVERTED | kept | 201 |
    | Step 4 throws, then succeeds on retry (3 attempts) | PAID | SOLD | kept | 201 |
    | Step 4 fails every attempt | **PENDING** | SOLD to it, hold CONVERTED | kept | 500 |
    | The compensating release throws | **PENDING** (not cancelled, not refunded) | unknown | kept | 500 |
    | A compensating cancel or refund throws | the other steps still run; logged | | | 500 / original |

    Once seats are sold, nothing is ever released or refunded: undoing a sale would refund a buyer
    who keeps seats, or leave SOLD seats without a PAID order. The two **PENDING** rows are the safe
    side of an unknown: the seats are not lost (or the order isn't refunded by mistake), only the
    order status is wrong, and the M1.7 invariant checker reports it.
  - Invariant I8 now counts the seats of ACTIVE **and CONVERTED** holds: a converted hold's seats
    are exactly its order's, and counting holds (not order items) avoids counting a seat twice while
    its order is PENDING and its hold still ACTIVE.
- **Why:**
  - A unique constraint is the simplest correct referee for "two requests, one hold": both pass the
    check in Java, Postgres lets one row commit and fails the other. No lock taken by hand.
  - Step-per-transaction keeps D-015 (the strategy owns its transaction and the hold → seats lock
    order), works for Redis, never holds a transaction open across the provider call, and is exactly
    the step list the M3 saga will persist. Step 1 must commit before step 3 anyway, because
    `event_seats.order_id` has a foreign key to `orders`.
  - Setting `order_id` only on sell needs no new transition, no extra inventory call and nothing new
    in Lua.
  - The unique hold link already makes a retry safe; building the general idempotency table here
    would be M3.1 pulled forward.
  - A provider swapped in tests keeps the main code free of a fail switch that the M3 chaos
    provider replaces anyway.
  - `sell` checks `expires_at > now()` under the hold lock, not just `status = 'ACTIVE'`: the sweeper
    runs every 5 s, so an ACTIVE hold can be past its expiry, and status alone would sell it.
- **Known limits (until M3):**
  - **A real process crash between steps** leaves a PENDING order: its active items keep its seats
    from every other order (409 SEAT_TAKEN), even after the sweeper frees the hold. No code here can
    run after a crash; M3's persisted saga resumes or compensates it.
  - The two PENDING rows of the failure table (step 4 never succeeds; the compensating release
    throws) end the same way.
  - **An unknown payment outcome stays CREATED** and is never closed here: the provider threw, or it
    succeeded and recording that failed (money moved, and its `provider_ref` may be lost). Closing it
    as FAILED could lose a real charge (found by the correctness review). M3's reconciliation asks
    the provider by payment id, which is the provider's idempotency key.
  - **An in-flight checkout blocks the seats for its duration.** Step 0 is an unlocked read and step 1
    doesn't re-check the hold, so a checkout whose hold ends while it pays keeps active items until
    step 3 cancels it; another buyer who holds those seats meanwhile gets 409 SEAT_TAKEN ("try again
    shortly"). Seconds with the synchronous fake provider; with M3's asynchronous payment it can be
    minutes, so M3 should re-check the hold in step 1 or order the seats' release after cancellation.
  - The step 4 retries are immediate, without backoff. Only `RuntimeException` is compensated; an
    `Error` (OutOfMemoryError, StackOverflowError) after step 1 ends like a crash.
  - SEAT_TAKEN on POST /orders lists all the hold's seats, not only the blocked ones. The constraint
    is recognised by its name in the Postgres message (the driver is runtime-only, so
    `PSQLException.getServerErrorMessage().getConstraint()` isn't available at compile time).
  - POST /orders doesn't check the event's status (paused or cancelled), like D-016's unlocked
    sale-window check.
  - `DELETE /holds/{id}` during an in-flight checkout still releases the hold; that checkout then
    refunds and answers 410.
  - No Idempotency-Key, so a retry that sends a **different** hold id is a new order (it is a
    different hold, so this is the caller's real intent or a client bug, not a double charge).
- **How I'd know it was wrong:** the M1.7 checker finds PENDING orders or SOLD seats without a PAID
  order outside a known crash; buyers see SEAT_TAKEN on seats that look free (crashed checkouts are
  more common than assumed, so M3 recovery is needed sooner); M2.4 load runs show `uq_orders_hold`
  violations from something other than double clicks; or M3's saga can't reuse these steps as they
  are.

### D-018 Signed tickets: JDK Ed25519, compact payload, issued after PAID (DRAFT)
- **Date:** 2026-11-10
- **Context:** M1.6 issues the tickets of a PAID order as the saga's TicketsIssued step (PRD 6.4)
  and signs them so a gate scanner can verify them offline with only a public key (PRD 6.9). Three
  choices were open: how to sign and encode the payload (a smaller payload is an easier QR code to
  scan), what happens when issuing fails after the order is already PAID (D-017: a sale is never
  undone), and what "holder" means in a payload anyone can read. Ticketing may not read inventory's
  or booking's tables (D-007), yet the wallet should show "Section A, Row 3, Seat 5".
- **Options considered:**
  - Signing: the JDK's built-in Ed25519; BouncyCastle (`bcprov-jdk18on`); Nimbus JOSE (already on
    the classpath) for a JWS, which needs Google Tink for Ed25519.
  - Payload: a compact binary format in base64url (195 characters); a hand-built JWS (about 400).
  - Issuing fails after PAID: retry, then keep PAID and answer 201; the same but answer 500; issue
    in the transaction that marks the order PAID.
  - Holder: the user id; a per-ticket HMAC of the user id; the name or email.
  - Seat labels: ids only (the frontend resolves labels); booking passes labels and ticketing keeps a
    snapshot.
- **Decision:**
  - **JDK Ed25519, no new dependency.** The key in the environment is the 32-byte seed
    (`STAMPEDE_TICKET_SIGNING_KEY`, base64), which PowerShell can generate. The JDK has no public
    "seed to public key" method, so `Ed25519Keys` hands the JDK key generator a random source that
    returns the seed, then checks that the private key it got back contains that seed. The signer
    signs and verifies a test message at startup, and `Ed25519KeysTest` checks the RFC 8032 vector.
    A missing, malformed or wrongly sized key (exactly 32 bytes) stops the app at startup.
  - **Compact binary payload, format 1:** format byte, 4-byte key id, ticket, event, seat and holder
    UUIDs, issue time in epoch seconds, version: 81 bytes, signed, then
    `base64url(payload).base64url(signature)`, 195 characters. Specified in docs/ticket-format.md
    with a test vector.
  - **Key id derived, not configured:** the first 4 bytes of SHA-256 over the raw public key. Stored
    on each ticket (V4 `tickets.key_id`) and published as `kid` by `GET /tickets/keys` (public, a
    JWKS with one OKP key today), so rotation can later publish several keys.
  - **Step 5 after step 4.** `CheckoutService` calls `ticketing::api` `TicketIssuer.issueForOrder`
    with the order, event, buyer and labelled seats, then records saga state TICKETS_ISSUED (guarded:
    only from PAID/SEATS_SOLD). Three attempts. If all fail, the order stays **PAID at SEATS_SOLD**,
    the answer is still **201**, and an error is logged; nothing is released or refunded. A retried
    `POST /orders` for the same hold (hold CONVERTED) re-runs issuing before answering 200.
  - **Idempotent by the database:** each insert is `ON CONFLICT (event_id, seat_id) WHERE status <>
    'REVOKED' DO NOTHING` on `uq_tickets_live_seat`, in one transaction with seats in id order;
    afterwards every seat's live ticket must belong to this order, or the whole issue rolls back
    and throws.
  - **Holder = user id only.** No personal data in a readable QR code.
  - **Seat labels as a snapshot** (V4 `section_code`, `row_label`, `seat_number`), passed by booking
    from inventory's checkout data (`CheckoutHold.CheckoutSeat`). Not signed: the scanner trusts the
    seat id, the label is for display. `GET /me/tickets` rebuilds the QR string from the stored row
    and signature; it never signs.
  - `issued_at` is whole seconds, set in Java, so the row holds exactly what was signed.
- **Why:**
  - The JDK does Ed25519 natively; one checked workaround is cheaper than an 8 MB library (or Tink)
    for one call. Ed25519 is deterministic, so no per-signature random nonce can go wrong.
  - 195 characters is roughly a 57×57 QR code at medium error correction, against roughly 81×81 for
    a JWS: fewer, larger dots scan more reliably from a phone screen in a queue. The cost is a format
    of our own, hence the spec and test vector.
  - After PAID the buyer has paid and has the seats; a 500 would call a successful purchase a
    failure, and the retry it invites returns the existing order anyway. Issuing in the PAID
    transaction would widen D-017's stuck-PENDING case for a failure that loses nothing.
  - The unique index already says "one live ticket per seat"; letting it decide races needs no lock
    taken by hand and keeps the guarantee even for callers that skip the Java checks.
- **Known limits:**
  - A PAID order can be without tickets until its buyer retries or M3 recovery runs; the wallet is
    empty meanwhile. The M1.7 checker should report PAID orders still at SEATS_SOLD.
  - One key, no rotation yet: changing `STAMPEDE_TICKET_SIGNING_KEY` makes earlier tickets fail to
    verify. Rotation means keeping old public keys in the key set (and in `TicketVerifier`).
  - The signing key is a plain environment variable, like the JWT secret; no HSM or KMS.
  - The signature proves authenticity, not current validity: a screenshot of a valid QR scans as
    valid until check-in records it (PRD's rotating QR is a stretch goal).
  - Seat labels are a snapshot; renaming a section after issue isn't reflected (seat labels don't
    change after seeding today).
  - Saga state is guarded by WHERE clauses in `OrderWriter`, not yet by a saga state machine class
    (M3 persists the saga).
- **How I'd know it was wrong:** a JDK upgrade fails the RFC 8032 test or startup self-test (then
  move to a library); gate scanners struggle to read the codes (then a smaller encoding such as
  base45 in alphanumeric mode); the checker often finds PAID orders without tickets (then issue
  asynchronously from an outbox event, M3); or a scanner vendor needs a standard format (then JWS
  or CWT).
